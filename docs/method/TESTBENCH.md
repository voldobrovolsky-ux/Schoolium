# Стенд: как агент тестирует спеку до того, как написан код

> Ключевая идея: **спеку можно исполнить**. Не целиком — но её FSM, её правила,
> её таксономии и её нагрузку на человека можно выразить в 150–300 строках
> одноразового кода, прогнать перечислением и увидеть дыры, которые чтением не
> видны. Это дешёвая форма lightweight formal methods: не доказательство, а
> исчерпывающий обход маленькой модели. Находка на модели стоит десятки минут;
> та же находка после реализации — недели и доверие школы.

## Уровни стенда

| Уровень | Что это | Стоимость находки | Ворота |
|---|---|---|---|
| **T0** | Линт спеки (P1…P7) | секунды | С4 |
| **T1** | Матрицы полноты: FSM и таксономии | минуты | С4 |
| **T2** | **Исполняемая модель** спеки: обход + свойства + симуляция | десятки минут | С5 |
| **T3** | Стенд на реальном рантайме: миграция + минимальный сервис + G-проверка | часы | реализация |
| **T4** | Живой смок (Chromium, реальный поток) | часы | релиз |

**Правило подъёма:** уровень не начинается, пока предыдущий красный. Спека не
идёт на T3, пока T2 не зелёный — иначе стенд на рантайме превращается в
отладку конструкции через инфраструктуру, самый дорогой способ думать.

---

## T2 — исполняемая модель (ядро метода)

Живёт в `specs/<id>/model/`. Одноразовый код, не продакшн: без БД, без Nest,
без сети. Его задача — **сломать спеку**, а не заложить архитектуру.

### Что в неё входит

**1. Состояния и переходы** — как данные, а не как код:

```js
export const states = ['draft','proposed','approved','conducted','locked'];
export const transitions = [
  { from: 'draft',     to: 'proposed',  by: 'teacher', event: 'ktp.submitted' },
  { from: 'proposed',  to: 'approved',  by: 'zavuch',  event: 'ktp.approved'  },
  { from: 'proposed',  to: 'draft',     by: 'zavuch',  event: 'ktp.rejected'  },
  // ...
];
export const terminals = ['locked'];
```

**2. Обход перечислением** (детектор L-2). Механически, не глазами:
- недостижимые состояния (нет входящего ребра от начального);
- тупики (нет исходящего ребра и состояние не терминал);
- отсутствие пути к терминалу из каждого состояния;
- переходы, не покрытые ни одной ролью (детектор L-8);
- состояния без экрана (сверка со списком экранов спеки — детектор L-15).

**3. Свойства (property-based)** — инварианты, которые обязаны держаться на
любой случайной последовательности допустимых действий:
- «оценка, выставленная учителем, читаема после любой последовательности
  изменений расписания» (L-1);
- «повторная доставка любого события не меняет итоговое состояние» (L-4);
- «ученик без согласия не появляется ни в одной производной выдаче» (L-13);
- «после отката КТП уже проведённые уроки не теряют содержание» (L-9).

Генерируется случайная последовательность из 200–2000 действий, инвариант
проверяется после каждого шага; при падении — минимизируется контрпример и
**прикладывается к находке**. Контрпример — это свидетель для правки спеки.

**4. Симуляция процесса** (детекторы L-16 и L-10) — синтетический день школы:
30 учителей × 6 уроков × 25 учеников. Считаем не производительность машины, а
**нагрузку на человека**: касания на массовое действие, переключения контекста,
количество экранов до первой пользы, число мест, которые надо тронуть, чтобы
добавить новый раздел.

**5. Конфликтные сценарии** — то, что обычно не описывают:
- двое пишут одновременно (учитель и завуч в одну клетку);
- действие приходит после отмены родительской сущности (оценка в отменённый урок);
- откат на предыдущую фазу с уже накопленными данными;
- отказ каждой внешней зависимости по очереди (детектор L-12).

### Что модель НЕ делает

Не проверяет производительность, не проверяет вёрстку, не заменяет
интеграционные G-проверки и **не подтверждает, что фича нужна**. Модель
проверяет внутреннюю связность конструкции, описанной спекой, — и только её.

### Обязательный раздел отчёта «что стенд не ловит»

Стенд, не нашедший ничего, — подозрителен. В `40-bench.md` всегда есть раздел с
перечислением классов дефектов, которые данная модель **не могла** обнаружить по
построению (например: «модель не содержит времени, поэтому дедлайны и
просрочки не проверены»). Этот раздел — основной источник заявок на новые линзы
(см. LENS-PROTOCOL §3).

## T3 — стенд на реальном рантайме

Когда T2 зелёный, а решение затрагивает схему или границы модулей: временная
ветка, миграция, минимальный сервис, реальный Postgres, скрипт-перечисление.
Скрипт **не выбрасывается** — он становится G-проверкой и переезжает в
`G-CHECKS.md` и CI. Так стенд конвертируется в постоянную фитнес-функцию, а не
в потраченное время.

**Правило нерушимости теста:** если стенд красный — правится спека или код, но
**не подгоняется проверка**. Изменение проверки допускается только вместе с
явным изменением АР-решения (наследуется из `G-CHECKS.md` §Правила ведения).

## Как агент решает, какой уровень нужен

| Признак задачи | Минимальный уровень |
|---|---|
| Новый экран поверх существующих данных | T0 + T1 |
| Новый FSM или новая роль в существующем цикле | + T2 (обход и свойства) |
| Новая сущность/таблица, новая граница модуля | + T3 |
| Внешняя интеграция | + T3, обязательный сценарий отказа |
| Массовое ежедневное действие пользователя | + T2 с симуляцией нагрузки (L-16) |
| Работа с персональными данными детей | + T2 со свойствами L-13 и обязательный T3 |

Уровень выбирается агентом самостоятельно на С4 и записывается в `40-bench.md`
до прогона — чтобы задним числом нельзя было объявить «здесь хватило T1».
