# Протокол АР-реестров: блоки ведения при сквозной нумерации

> Один реестр на весь проект перестаёт работать примерно на сотом решении: он
> становится лентой, в которой нельзя ни найти владельца, ни понять, что
> устарело. Дробление реестра по блокам ведения возвращает адресность. Но
> дробление номерных пространств ломает ссылки — поэтому **номер остаётся
> сквозным по всей системе, а файл определяет только блок ведения**.

## 1. Что такое блок ведения

Блок = зона, у которой **один владелец и один ритм изменений**. Не «модуль
кода» и не «раздел спеки»: решения о правовом контуре и решения о клиентском
рантайме меняются по разным поводам и разными людьми, даже если касаются одного
экрана.

Действующие блоки EduStore (`docs/ar/`):

| Файл | Блок | Предмет решений |
|---|---|---|
| `truth.md` | Источники истины и изоляция | Кто авторит факт, где граница тенанта, что канон |
| `platform.md` | Стек и рантайм | Язык, БД, деплой-юнит, транспорт, контракты фронт↔бэк |
| `events.md` | Событийная архитектура | Конверт, канон имён, доставка, каскады, дедуп |
| `roles.md` | Владение, роли, права | Оси ролей, разделение обязанностей, каталог прав |
| `law.md` | Право и безопасность детей | 152-ФЗ, миноры, согласия, аудит, retention |
| `domain.md` | Учебный процесс | КТП/КПП, расписание, парсер, движок предметной области |
| `ui.md` | Интерфейс и клиент | Маршруты, PWA, деградация клиента, дизайн-системы |
| `product.md` | Продукт, рынок, запуск | Позиционирование, SKU, последовательность запуска |

Новый блок заводится, когда у группы решений появляется **отдельный владелец
или отдельный ритм** — а не когда файл стал длинным.

## 2. Нумерация

1. **Номер сквозной по всей системе.** `AR-64` — единственный `AR-64`, в каком
   бы файле он ни лежал. Ссылка `AR-64` из любой спеки однозначна.
2. **Номер выдаётся из общего пула** блоками. Каждый реестр объявляет свои
   диапазоны в машинно-читаемой шапке:
   ```
   <!-- ar-register: id=platform; ranges=8-15,36-37 -->
   ```
   Диапазоны реестров не пересекаются; это проверяется линтером.
3. **Новый реестр начинается со следующего свободного номера.** Если выдано
   1–63, второй реестр открывается с 64. Первый диапазон нового реестра —
   блок из 20 номеров (`64-83`); исчерпав его, реестр получает следующий
   свободный блок, а не «вклинивается» в чужой.
4. **Номер не переиспользуется никогда** — ни после отмены, ни после слияния.
5. **Номер не меняет блок.** Если решение по смыслу переехало — старая строка
   получает статус `[заменено AR-N]`, новая строка получает **новый номер** в
   нужном реестре. Так история ссылок из старых спек остаётся читаемой.
6. **Индекс** `docs/ar/INDEX.md` — единственное место, где написано, какой номер
   выдавать следующим (`next`). Линтер сверяет его с фактическим максимумом.

## 3. Формат строки

```
| AR-64 | Формулировка решения + однострочное «почему» | [РЕШЕНО] | G-19 | L-6, L-12 |
```

| Колонка | Правило |
|---|---|
| № | `AR-N`, сквозной |
| Решение | Одна формулировка + «почему». Два решения в одной строке — дефект: делить |
| Статус | `[РЕШЕНО]` · `[дефолт]` · `[узел]` · `[заменено AR-N]` · `[отменено]` |
| Ворота | `G-n` (существующая или заведённая в «недостающих») либо `нет: <причина>` |
| Линзы | Какие линзы стерегут это решение (`L-n`) |

**Статусы:**
- `[РЕШЕНО]` — основания достаточны, не зависит от неизвестной информации.
  Обязаны быть ворота.
- `[дефолт]` — разумный выбор по умолчанию, владелец может изменить. Ворота
  желательны, но допустимо `нет: <причина>`.
- `[узел]` — решить нельзя без внешней информации. Угадывание здесь запрещено;
  у узла указывается, **чего именно не хватает и от кого**.
- `[заменено AR-N]` — решение вытеснено другим; строка остаётся навсегда.
- `[отменено]` — решение отозвано без замены; указывается почему.

## 4. Правила ведения

1. Каждый `[РЕШЕНО]` имеет ворота: существующую G-проверку либо новую строку в
   «недостающих» `G-CHECKS.md` **в том же коммите**.
2. Каждое решение указывает линзы, которые его стерегут. Решение, которое не
   стережёт ни одна линза, — сигнал: либо линзы неполны, либо решение не
   архитектурное.
3. Понижение статуса (`[РЕШЕНО]` → `[узел]`) — легальная операция, но считается
   в метрике M5. Систематические реверсы означают преждевременную фиксацию.
4. Реестр не пересказывается в спеках. Спека ссылается `AR-N` и описывает
   поведение; дублирование формулировки решения в спеке — источник расхождения.
5. Строки не удаляются. Реестр — журнал, а не текущее состояние.

## 5. Машинная проверка (`tools/method/lint-ar.mjs`)

- уникальность номеров по всем реестрам;
- отсутствие дыр в сквозной нумерации `1..max`;
- номер лежит внутри объявленных диапазонов своего реестра;
- диапазоны реестров не пересекаются;
- `next` в `INDEX.md` равен `max + 1`;
- статус — из допустимого множества;
- у каждого `[РЕШЕНО]` непустые ворота корректного формата;
- каждая ссылка `AR-N` из любого документа `docs/` указывает на существующее решение;
- каждая ссылка `G-n` указывает на строку в `G-CHECKS.md`;
- каждая ссылка `L-n` указывает на линзу в `LENSES.md`;
- `[заменено AR-N]` указывает на существующий номер.
