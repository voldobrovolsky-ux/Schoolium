# Кабинеты Schoolium 1.3.0

Единственное место операционной матрицы «что администрируется где» (П-5):
спеки и реестры ссылаются сюда, а не повторяют таблицу. Решения —
AR-186…AR-194 в [docs/ar/](./ar/INDEX.md); доказательства — G-81…G-83 в
[G-CHECKS.md](./G-CHECKS.md).

## 1. Три кабинета

Кабинет открывается **по праву, а не по роли** (AR-186): человек с двумя
ролями видит оба кабинета одной учёткой; роль без права получает 403 с
причиной, а не пустую страницу и не молчаливый редирект (AR-69).

| Кабинет | Для чего | Маршрут | Экран | Право | Кто |
|---|---|---|---|---|---|
| Администратор | сеть и устройства всех людей школы, политика доступа, реестры, полный аудит | `/admin`, `/admin/:section` | `S-62` | `school.admin` | `admin` |
| Модератор | КПЦ (классы, ученики, родители, персонал, активации, коды, пароли) и панель УТЦ (предметы, привязки, сборка расписания) | `/moderator` | `S-60` | `school.manage` | `moderator`, `admin` |
| Завуч | чек-листы готовности УТЦ и КПЦ, сводки; единственная мутация — нормы часов на `/schedule` | `/deputy` | `S-61` | `school.oversee` | `deputy_academic`, `admin` |

До 1.3.0 кабинет модератора жил на `/admin`. Закладка модератора на `/admin`
теперь открывает 403 «Раздел доступен администратору школы».

Входы в кабинеты: десктоп — пункты сайдбара `L.sidebar.item.admin` /
`.moderator` / `.deputy` (каждый виден только при своём праве); мобайл —
кнопка хедера `L.header.admin` ведёт в старший доступный кабинет, остальные
— в меню пользователя `M-15`. Кабинеты не являются шестой вкладкой таб-бара
(AR-81).

## 3. Карта устройств (`S-62`, раздел «Устройства»)

Источник — строки `AppSession` с полями происхождения (AR-187). Карта
ничего не хранит сама.

| На карте | Что это по данным |
|---|---|
| Линия от человека к устройству | прямой вход: пароль, код входа, ссылка входа — `parentSessionId` пуст |
| Линия от телефона к устройству | подключение сканом с телефона (паттерн Telegram, AR-94): `parentSessionId` = сессия телефона; узел вложен под сессию телефона |
| «в приложении» / «в браузере» | `clientKind`: `pwa`, если клиент прислал заголовок `x-schoolium-client` из режима `display-mode: standalone`; иначе `browser` |
| «в сети» | `lastSeenAt` не старше 15 минут (`ACCESS_PARAMS.sessionOnlineMinutes`) [дефолт]; иначе показано время последней активности |
| «новая сеть» (`data-new-network`) | первая сессия этого человека из подсети /24, которой нет в его истории за 90 дней — включая уже погашенные сессии |
| Адрес | элемент `X-Forwarded-For`, отстоящий от конца на `TRUSTED_PROXY_HOPS` доверенных прокси (по умолчанию 2: Caddy и web-nginx, `.env.prod.example`); первый элемент дописывает сам клиент, поэтому по нему не судят; страна и город не определяются — geo-IP нет |
| `data-status="ended"` | сессия отозвана или истекла; хранится 90 дней после этого (AR-194), затем удаляется ежедневной чисткой |
| Фильтр `S-62.devices.search` | по ФИО и юзернейму — единственный поиск в приложении, потому что карта всей школы без него нечитаема |

Персонал в карте идёт впереди учеников и родителей. Причины завершения
сессии в журнале подключений `M-29`: `manual` (сам человек, `S-80`),
`admin` (администратор, адресно), `incident`, `limit`, `deactivated`,
`deleted`, `activation_revoked`.

## 4. Дистанционная активация (ссылка входа)

Для сотрудника, который не может подойти к модератору за именным QR или
кодом. Выпускают модератор и администратор — право `staff.manage` (AR-204,
вытесняет AR-189 и AR-195).

1. `S-31` карточка сотрудника → селекты `S-31.select.linkTtl` (24 ч, 48 ч,
   7 дней; дефолт 48 ч) и `S-31.select.linkUses` (1, 3, 10, без лимита;
   дефолт без лимита) → `S-31.btn.loginLink` «Ссылка для входа»; либо
   `S-62` → «Устройства» → человек → `S-62.devices.btn.grant` «Выдать вход»
   с дефолтами. Условие: штатная учётка с карточкой.
2. Сервер выпускает ссылку `BootstrapLink` с `purpose = login_link`,
   `issuedBy` = выпустивший, `expiresAt` по сроку, `maxUses` (число либо
   без лимита) и счётчиком `useCount`; событие `staff.login_link.issued.v1`
   (+ `ttlHours`, `maxUses`) ложится в аудит с идентичностью.
3. Блок `S-31.loginLink` / `S-62.devices.link`: URL, QR, «Скопировать»,
   «действует до …, использований N из M» либо «без лимита». Передать
   человеку любым каналом, которому выпустивший доверяет.
4. Человек открывает ссылку: членство активируется (AR-161), выдаётся
   сессия канала `login_link`, открывается стартовый экран роли; `useCount`
   растёт на единицу в той же транзакции.
5. Повторное открытие в срок и в пределах лимита — новая сессия (телефон и
   ноутбук по одной ссылке); исчерпание лимита — `LINK_EXHAUSTED` («Ссылка
   использована 3 из 3 раз — попросите выпустить новую»); после срока —
   `TOKEN_EXPIRED`. И то и другое лечится перевыпуском той же кнопкой,
   истёкшая или исчерпанная ссылка не оживает.

Та же ссылка выпускается консолью для администратора, модератора и завуча
(`school:provision`, workflow `action=provision`) — `purpose = bootstrap`,
`issuedBy` пуст. Порядок для прод-стенда — [PROD-STATUS.md](./PROD-STATUS.md).

## 5. Инцидент-режим

Когда: утерянное устройство с живой сессией, подозрение, что чужой вошёл
под чьей-то учёткой, массовый вход из неизвестной сети (AR-188).

1. `S-62` → «Политики» → карточка `S-62.policy.incident` → «Закрыть все
   сессии школы» → `M-28`. Текст называет число живых сессий; сессия
   администратора остаётся.
2. `POST /api/v1/admin/sessions/revoke-all`: каждая сессия школы, кроме
   текущей, получает `revokedReason = incident`; на каждого человека —
   запись аудита `staff.session.revoked.v1`; в политике сохраняются
   `incidentAt` и `incidentBy`.
3. Люди входят заново любым каналом — QR, код, пароль, ссылка;
   администратор в этом не участвует. Флага «вход закрыт» нет: закрыть
   человеку вход — это деактивация учётки (AR-89), не инцидент.
4. Адресный случай (одно устройство) — не инцидент: `S-62.devices.btn.revoke`
   «Завершить» у сессии, причина `admin`.

Лимиты сессий (`S-62.policy.limits`) — не инструмент инцидента: лимит
работает на входе и гасит самую давнюю сессию человека (`limit`), но во
входе не отказывает никогда. Лимиты носителей ролей (`S-62.policy.roleLimits`,
AR-205) — тоже не про инцидент: они держат число людей с ролью в школе при
заведении карточки, выдаче роли и реактивации (`ROLE_LIMIT_REACHED`: «Директор:
в школе уже 1 из 1 носителей роли — лимит задаёт администратор в «Политиках»»),
сессий не касаются; дефолт 1 у директора и обоих замов, у остальных штатных
ролей — без лимита; подпись «занято N» считает живые членства и пустые слоты.

## 6. Чего в кабинетах нет намеренно

| Нет | Почему |
|---|---|
| Биллинг, тарифы, оплата | оплата вне сайта (`docs/ONBOARDING.md`); школу заводит владелец продукта консолью (AR-93), кабинет школы денег не видит |
| Geo-IP (страна, город по адресу) | внешних вызовов у контура доступа нет (AR-187 [дефолт]); адрес — сетевой след для «новой сети», не координата |
| Флаг блокировки входа | закрыть вход — деактивация с каскадом (AR-89); «замок» без деактивации — отдельное решение владельца, слот (AR-188) |
| Массовое удаление и массовое выделение | удаление и деактивация — по одной записи из её карточки с названным объёмом потери (AR-89, AR-105); `70-screens.md` §10 |
| Редактирование матрицы прав | каталог прав — код `packages/shared` (AR-35); матрица в `S-62` читается, правка — коммит с воротами G-10 |
| Экспорт адресов и журнала подключений | адрес виден только администратору и никуда не выгружается (AR-194) |
| Просмотр чужих паролей | показ пароля = перевыпуск (`S-31.btn.reissuePassword`) или задание нового (`M-32`, AR-203); текущий пароль не выдаётся никогда (AR-156) |
