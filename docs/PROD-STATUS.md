## Ветки и снапшоты деплоя (решение владельца 2026-08-30)

Постоянных веток две: **`main`** (с неё деплой) и **`work-line`** (интеграция,
CI). Короткоживущие `claude/*` агентных сессий вливаются в `work-line`/`main` и
удаляются сразу после мержа. Снапшоты деплоя — **теги, не ветки**: после каждого
зелёного health-check workflow сам ставит неизменяемый тег `deploy/<дата>-runN`
и передвигает алиасы `deploy-current` / `deploy-previous`. Откат = запуск
workflow с предыдущим тегом. Руками теги не двигать.

## Канал деплоя — только через GitHub Actions

Агентная среда (сессии Claude Code на удалённом раннере) не имеет прямого SSH
до VPS — наружу только HTTPS через прокси. Деплоить может **только** раннер
GitHub, у которого есть SSH-ключ в секретах репозитория. Это не временное
ограничение, а архитектурное решение — см. комментарий в самом workflow.

- Workflow: `.github/workflows/deploy-school.yml`, запуск — `workflow_dispatch`.
- Actions: `deploy` (полный выкат кода + сборка + запуск), `bootstrap` (завести
  школу/оператора), `provision` (учётки администратора, модератора и завуча СУЩЕСТВУЮЩЕЙ
  школы со ссылками входа на 48 ч (многоразовыми до истечения, AR-195); только добавляет,
  существующие учётки и данные не трогает),
  `import` (залить данные школы), `schedule-clear` (убрать ОШИБОЧНУЮ сетку
  школы: шаблоны и пустые уроки удаляются, уроки с отметками отвязываются;
  классы/предметы/привязки/нагрузка/ученики не трогаются; требует workspace),
  `status` (только читает, ничего не меняет — безопасно вызывать в любой
  момент для диагностики).
- Секреты уже настроены (Settings → Secrets and variables → Actions):
  `VPS_HOST`, `VPS_USER`, `VPS_SSH_KEY`. `DATA_KEY` нужен только для `import`.
- У пользователя также есть свой SSH-ключ (Windows, `C:\Users\<user>\.ssh\test123`)
  с доступом `root@188.225.74.252` — для ручной диагностики, если понадобится.

## ⚠️ На сервере уже реальные данные — не тестовый стенд

По состоянию на 2026-08-30 в базе — **87 реальных учётных записей учеников**
(результат более раннего прогона, до текущей сессии). Действовать соответственно.

**Никогда не выполнять на этом сервере:**
- `docker compose down -v` — сносит именованный том `pgdata`, то есть базу
  целиком, вместе со всеми учениками. Без явного запроса пользователя и
  подтверждения, что данные не нужны — не трогать вообще.
- любое пересоздание/удаление тома `pgdata`.
- смену `POSTGRES_PASSWORD` в `.env.prod` без синхронизации с реальным паролем
  в базе (иначе повторится инцидент ниже).

## Инцидент 2026-08-30 (для контекста, уже исправлено)

Первый прогон `deploy` после настройки секретов завершился зелёным, но API
падал в busy-loop: `P1000: Authentication failed against database server`.
Причина: на сервере уже стоял более ранний прогон с другим паролем БД, а
`.env.prod` внёс новый — пароли разошлись.

Исправлено без потери данных: в workflow добавлен шаг «Синхронизировать
пароль БД с .env.prod» — на каждом `deploy` выставляет базе пароль из
текущего `.env.prod` через доверенный локальный сокет внутри контейнера
`postgres` (`ALTER USER ... WITH PASSWORD ...`), таблицы и volume не трогает.

Заодно исправлен health-check: реальный роут — `/api/healthz` (global prefix
`api`, см. `apps/api/src/main.ts` + `HealthController` в
`apps/api/src/schoolium/observability/observability.module.ts`), раньше
скрипт стучался в несуществующий `/api/v1/health` и получал 404 даже когда
API был жив.

## Инцидент 2026-08-31: «задеплоено» не значило «доехало» (исправлено)

Вечерний пакет прошёл CI, деплой был зелёным, health-check отвечал 200 — а
владелец не видел изменений ни с телефона, ни с десктопа, и обновление
страницы не помогало. Кода это не касалось: он лежал на сервере с 09:26 UTC.

Причина — service worker. `apps/web/public/sw.js` копировался в `dist` **без
обработки**, поэтому был байт-в-байт одинаков 68 коммитов подряд. Браузер
ищет обновление воркера сравнением БАЙТОВ скрипта: одинаковые байты значат
«обновления нет», `install`/`activate` не выполнялись ни разу с первой
установки, а стратегия «сначала кеш» отдавала прошлую оболочку. Обновление
страницы в этот контур не входит — F5 идёт через тот же обработчик.

Исправлено (AR-185): воркер СОБИРАЕТСЯ из `apps/web/src/sw-source.js` с
подстановкой идентификатора сборки (байты меняются каждый релиз), навигация —
network-first мимо HTTP-кеша, хешированные `/assets/` — cache-first в
отдельном кеше, `index.html`/`sw.js`/манифест отдаются с `no-cache`.

**Гейт, которого не хватало**: шаг «Проверка веб-контейнера (релиз доехал до
браузера)» в `deploy-school.yml`. Раньше деплой гейтился ТОЛЬКО на
`/api/healthz` — про веб-контейнер пайплайн не знал ничего. Теперь прогон
падает, если бандл из `index.html` не отдаётся, воркер не несёт идентификатор
этой сборки или оболочка отдаётся кешируемой.

**Цена, которую надо помнить при следующих выкатах**: устройство, уже
залипшее на прошлой оболочке, расклеивается со ВТОРОГО открытия — первое ещё
исполняет прошлый бандл. Мгновенно — открыть адрес с любым неиспользованным
параметром (`https://schoolium.store/?v=2`).

Отдельно исправлен дефект того же прогона: `docker compose exec -T postgres
psql …` внутри heredoc съедал остаток скрипта из stdin — строка
`restart api` не выполнялась ни разу, а сам psql висел в ожидании EOF и убил
прогон №17 по таймауту SSH («Broken pipe» через 15 минут). Добавлен
`< /dev/null`.

## Быстрые команды

- **Проверить, что стенд жив, ничего не меняя**: GitHub Actions → workflow
  `deploy-school` → Run workflow → `action=status`.
- **Задеплоить новый код**: тот же workflow → `action=deploy`, ветка обычно
  `main`. Синхронизирует код (rsync), пересобирает образы, перезапускает
  контейнеры. Volume `pgdata` не трогает.
