# Рекогносцировка Schoolium 1.3.0 (2026-09-02)

Проверялся пакет 1.3.0: ветка `claude/schoolium-admin-cabinet-ui-rntrn6`,
голова `66d0088`, документ пакета `docs/CHANGES-2026-09-02.md`. Новых функций
не писалось. Правила: `CLAUDE.md`, `docs/PROD-STATUS.md` (прод-сервер не
трогался ни одной командой), семь правил `flor-platform-docs/CLAUDE.md` §1.
Формат каждого пункта — **факт → чем доказан**. «Работает» пишется только со
ссылкой на зелёную проверку (П-7).

Стенд: контейнер сессии, Node 22.22, Postgres 16.13 (локальный кластер),
Chromium 1194 из `/opt/pw-browsers`, Playwright 1.55 из `node_modules`.
Скриншоты — `docs/recon-2026-09-02/`, сценарии стенда там же
(`stand.mjs`, `stand-devices.mjs`; запускаются с `STAND_OUT=<каталог>` из
корня репозитория, поднимают API и web сами, база `edustore_recon`).

## 0. Итог одним абзацем

Пакет собирается, все ворота и оба смока зелёные локально и в CI, три кабинета
открываются по праву и закрываются 403 с причиной, ссылки входа 48 ч работают
консолью и с карточки, вход по коду и по паролю на телефоне работает, скан QR
с экрана входа подключает второе устройство и вкладывает его под телефон на
карте, лимит сессий гасит давние сессии с причиной «лимит сессий», инцидент-режим
закрывает всё, кроме сессии администратора. **Блокирующих эксплуатацию дефектов
не найдено.** Найдено 3 дефекта уровня «мешает» (карта устройств приписывает
подключённому сканом устройству браузер, адрес и вид клиента телефона-сканера;
чек-лист завуча показывает «0 из 0» вопреки AR-193/G-82, и ворота этого не
ловят; выброшенный из системы человек не узнаёт причину) и ряд полировки —
таблица в §8.

## 5. Сеть и устройства

Сценарий `stand-devices.mjs` (`stand2.log`): модератор вошёл паролем на
«телефоне» (контекст Android); «ноутбук» (второй браузерный контекст,
1440×900) открыл `/login` с QR (`05-laptop-login-qr.png`). QR снят с экрана
ноутбука в JPEG и подан телефону как кадр **поддельной камеры Chromium**
(`--use-file-for-fake-video-capture`, MJPEG). Телефон: `/settings/devices` →
«Подключить устройство» → видоискатель (`05-phone-viewfinder.png`) →
**камера распознала QR** → `S-80.confirm` «Подключить устройство?»
(`05-phone-confirm.png`) → «Подключить» → ноутбук получил сессию и ушёл на
`/classes`.

- API `GET /v1/admin/devices`: сессия ноутбука `via=device_link`,
  `parentSessionId` = сессия телефона; сессии прямого входа без родителя.
- DOM карты: узел ноутбука — на глубине 2 `ul.sch-adm-tree`, вложен под
  узел телефона (`05-admin-map-nested.png`, `05-phone-admin-map-nested.png`).
- **Но** узел ноутбука подписан «Chrome · Android», адрес и вид клиента у него —
  телефона: `approveDeviceLink` берёт `deviceHint/clientKind/ip` из запроса
  сканирующего телефона (`access.service.ts:120-127`, `clientOf(req)` в
  `access.controller.ts:34-42`), а не из запроса ноутбука, выпустившего токен.
  На списке `S-80` телефона ноутбук — «Chrome · Android … подключена с
  телефона». Дефект Д-1 в §8.

**Лимит сессий 1 для роли модератора** (`#limit-moderator` → 1 → «Сохранить»;
`GET /admin/policy` → `moderator: 1`, `05-admin-policy-limit.png`). У модератора
было две живые сессии (ссылка, код). Новый вход паролем **не отклонён**

контекст модератора: `/me` → 403, экран входа без объяснения (Д-3).
