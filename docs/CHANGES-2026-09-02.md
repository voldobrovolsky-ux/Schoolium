## 1. Как читать изменения по слоям

### Контракт (`packages/shared/src/schoolium.ts`)
- Права: `school.admin` (новая мутационная группа, только `admin`),
  `school.oversee` (надзорная группа, `deputy_academic` и `admin`).
- Параметры: `bootstrapLinkTtlHours` 24 → 48, `loginLinkTtlHours` 48,
  `sessionOnlineMinutes` 15, `sessionJournalDays` 90.
- DTO кабинетов: `AdminOverviewDto`, `AdminDeviceMapDto`, `AdminSessionDto`
  (канал, вид клиента, адрес, родительская сессия, «новая сеть», `current`),
  `AccessPolicyDto`/`SessionLimits`, `SchoolAuditEntryDto`, `LoginLinkDto`,
  `StaffActivityDto`, `SchoolNetworkDto`, `SchoolAssetDto`, `IncidentResultDto`,
  `DeputyCabinetDto`/`ChecklistItemDto`; `SessionDto` расширен.
- Словари слов — одни на все экраны: `SCHOOL_STATE_LABELS`,
  `SESSION_VIA_LABELS`, `SESSION_CLIENT_LABELS`, `SESSION_REVOKE_REASON_LABELS`.
- Стартовый экран завуча — `/deputy`.

### База (`apps/api/prisma`)
Одна миграция `20260902090000_admin_cabinet_130`, только расширение:
`AppSession.via/clientKind/ip/parentSessionId`, `BootstrapLink.purpose/issuedBy`,
таблицы `SchoolNetwork`, `SchoolAsset`, `SchoolAccessPolicy` (все три под
tenant-guard). Откат кода на прежний тег остаётся возможным: старый клиент
лишних колонок не читает. Миграцию применяет контейнер API при старте
(`Dockerfile`: `prisma migrate deploy`), отдельного шага в деплое нет.

### API (`apps/api/src/schoolium`)
- `cabinets/`: `AdminCabinetController` (`/v1/admin/*`, всё под `school.admin`),
  `ModeratorCabinetController` (`/v1/moderator`, бывший `/v1/admin`),
  `DeputyCabinetController` (`/v1/deputy`), общая проекция сессии
  `session-view.ts` (адрес виден только администратору — AR-194).
- Сессии: `SchoolSessionService.issue` пишет канал, вид клиента (заголовок
  `x-schoolium-client`), адрес (первый хоп `x-forwarded-for`) и родительскую
  сессию; лимит по роли выталкивает самую старую сессию (причина `limit`), а
  не отказывает во входе; суточная очистка журнала старше 90 дней.
- События: `staff.login_link.issued.v1`, `school.policy.set.v1`,
  `school.registry.changed.v1` (всего 25); причина отзыва расширена
  (`incident`, `limit`, `admin`). Каждое действие администратора — в аудите с
  идентичностью.
- Персонал: `POST /v1/staff/:id/login-link` (48 ч, `school.admin`),
  `GET /v1/staff/:id/activity` (`staff.manage`).
- Консоль: `school:provision` заводит завуча (`--deputy-name/--deputy-username`);
  workflow `deploy-school.yml` получил вход `deputy`.

## 3. Чего в пакете нет и почему

- **Биллинг** — по указанию владельца: контура оплаты нет, раздел не заводится.
- **Гео-IP** — внешних вызовов нет; «новая сеть» считается по /24 из истории
  самого человека [дефолт].
- **Блокировка входа как режим** — инцидент-режим одноразовый: закрыть все
  сессии; флага «вход закрыт» нет (слот).
- **Массовое удаление** — не вводится (AR-89).
- **Уведомления, брендинг, экспорт, резервные копии** — вне первой версии;
  перечислены в аудите `flor-platform-docs`.

## 4. Как выпустить ссылки трём ролям

1. Задеплоить пакет: workflow `deploy-school` → `action=deploy`, ветка с пакетом.
2. Тот же workflow → `action=provision`, входы `admin="Фамилия Имя=username"`,
   `moderator="Фамилия Имя=username"`, `deputy="Фамилия Имя=username"`
   (существующие учётки не пересоздаются, только перевыпускается ссылка).
3. В логе прогона — три одноразовые ссылки на 48 часов. После деплоя ссылку
   любому сотруднику выпускает и администратор с карточки `S-31`.
