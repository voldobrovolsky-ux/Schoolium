# Вход 1.3 · Запрос владельца и реестр решений

Пакет инкремента «Вход 1.3»: контур создания пользователя и входа в кабинет.
Основание — описание владельца от 2026-08-30 и карта готовности (воркфлоу-аудит
12 агентов, той же датой). АР-пакет внесён в блочные реестры: **AR-164…AR-170**
(см. `docs/ar/platform.md`, `ui.md`, `truth.md`). UI-спека — `70-screens.md`
этого пакета (Draft, вычитывается владельцем отдельной сессией).

## 1. Целевое описание (сжато, слова владельца)

1. Пользователя создаёт **админ школы в кабинете** и **владелец/Claude командой
   в терминале** (владелец — на сервере, Claude — через workflow).
2. Пользователь несёт Фамилию, Имя, юзернейм, пароль; при создании
   автоматически формируется **ссылка на кабинет** — 15 минут с момента
   выпуска.
3. Созданный появляется в КПЦ, раздел «Пользователи»: список с фильтрами
   (авторизованные / неавторизованные / удалённые), клик — модальное окно
   (ID, username, password, Name, Surname) с кнопками **QR · URL · 6-значный
   код**.
4. QR сканируется обычной камерой (до входа) → сразу в кабинет; URL открывается
   в браузере → сразу в кабинет; 6-значный код вводится на сайте **только после
   выбора школы**.
5. Вход через сайт: по дефолту QR (сканирует телефон с активным кабинетом:
   профиль → настройки → устройства → привязать устройство → камера → «успешно»
   → возврат на главную); либо «войти по юзернейму и паролю»; код с корня сайта
   не работает.
6. Лендинг: школы уезжают вниз **лентой-каруселью** (слева направо, как
   логотипы партнёров), клик по карточке школы → экран школы со входом:
   код / юзернейм+пароль / QR.

## 2. Реестр решений (утверждены владельцем 2026-08-30: «согласен со всеми рекомендациями»)

| № | Узел | Решение | АР |
|---|---|---|---|
| У-1 | password в модалке против bcrypt-only (AR-156) | **Показать = перевыпустить**: кнопка генерирует новый пароль, показ один раз; текущий пароль не выдаётся никогда | AR-169 |
| У-2 | «ссылка только от владельца/Claude» против кнопок в модалке админа | **Артефакт один, каналов выпуска два**: автовыпуск при создании (платформа) + кнопки модалки (модератор/админ) | AR-165 |
| У-3 | скоупинг 6-значного кода школой (против AR-163) | **Скоупить**: verify принимает школу, работает только с экрана школы; `/login/code` с корня выводится; отказ единый `LOGIN_CODE_INVALID` | AR-166 |
| У-4 | код только у персонала | **Распространить** на учеников и родителей | AR-166 |
| У-5 | фильтр «удалённые» против hard-delete (AR-89/78) | **v1: «удалённые» = деактивированные**; GuardianCard получает деактивацию; тумбстоун — слот с юр-оценкой 152-ФЗ | AR-168 |
| У-6 | «URL сразу в кабинет» против гейта чужой сессии (AR-91) | **Гейт сохранить**, определять «чужую» по валидной сессии, дать действие «Выйти и продолжить» | AR-170 |
| У-7 | кратность ссылки (QR+URL = одна ссылка) | **Одноразовая** (AR-109): открытие любого представления гасит оба; повтор — перевыпуском | AR-165 |
| У-8 | три TTL рядом (5 мин / 15 мин / 24 ч) | **Развести явно**: код 5 мин · ссылка на кабинет 15 мин · bootstrap 24 ч | AR-165 |
| У-9 | «пользователь вообще» не существует в модели | **Команда называет роль** и создаёт карточку-носителя | AR-164 |
| У-10 | вход по коду не ставил activatedAt | **Любой первый успешный вход активирует** учётку | AR-168 |
| У-11 | канал доставки owner-ссылки — лог workflow | **Принять с названной ценой**: быстрый action `user-create` без деплоя; пароль в лог только по явному флагу | AR-164, AR-165 |
| У-12 | карусель при 1–2 школах вырождается | **Порог**: до 5 школ — статичный ряд; `prefers-reduced-motion` всегда | AR-167 |

## 3. Фикс-пакет действующего контура (идёт первым, AR-170)

| № | Дефект (живёт в проде) | Класс |
|---|---|---|
| Б-1 | Cookie после активации по QR — сессионная (без maxAge): закрытие браузера разлогинивает главный канал онбординга | крит |
| Б-2 | «Чужая сессия» на `/join` определяется наличием cookie, не валидностью — мёртвая cookie даёт ложный отказ | крит |
| Б-3 | Активация гасит токен и ставит `activatedAt` **до** ветки «чужая сессия» — токен сожжён, входа не было | крит |
| Б-4 | Перебор 6-значных кодов не ограничен ничем (анонимный verify, 10⁶) | крит |
| Б-5 | Одноразовость всех четырёх токенов не атомарна (check-then-act): два устройства по одной ссылке — две сессии | важно |
| Б-6 | Статус-эндпоинт привязки бессрочно раздаёт cookie сессии по id токена | важно |

## 4. Не в объёме

- Тумбстоун/soft-delete учёток — слот (юр-оценка хранения ПДн детей).
- SMS и внешние каналы доставки ссылок (AR-94: SMS-контур не строится).
- Самостоятельная регистрация (AR-95 в силе).
- Усиление протоколов безопасности сверх фикс-пакета — слот версии ~1.4 (AR-94).

## 5. Порядок реализации

1. Фикс-пакет Б-1…Б-6 (AR-170) — отдельным изменением, до фич.
2. Схема/контракты: `GuardianCard.deactivatedAt`, `DeviceLinkToken.deviceHint`,
   verify со школой, `GET /v1/schools/:id`, `GET /v1/users`, login-code для
   student/guardian, скрипт `user:create` + workflow-action.
3. Экраны по `70-screens.md` этого пакета (после вычитки владельцем —
   статус Accepted).
4. Ворота G-71…G-74 (строки заведены в `docs/G-CHECKS.md` §Недостающие) — в том
   же изменении, что и реализация (П-4).
5. Паспорт блока «Доступ» — `docs/blocks/access.md` по
   `flor-platform-docs/guides/element-passport.md`, из материалов этой спеки.
