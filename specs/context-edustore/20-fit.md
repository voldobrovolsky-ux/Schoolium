## Разборы, где решение неочевидно

### Р1 · `worknet` — ключ изоляции или атрибут?
Соблазн: раз worknet — биллинг-сущность, ключевать данные и на неё, чтобы сеть
видела свои школы. Отклонено: второй ключ изоляции означает **две границы**, а
значит два места, где можно ошибиться, и запрос, который «почти изолирован».
Схема уже содержит `Workspace.worknetId` — этого достаточно: агрегация по сети
строится явным перечислением школ сети, а не ослаблением tenant-guard.
Зафиксировано в **AR-44**, доказывается **G-22**.

### Р2 · Область уникальности телефона *(требует подтверждения владельца)*
Формулировка постановки — «уникальный ключ **внутри workspace** школы».
Буквальное чтение даёт запись пользователя **на школу**: один человек,
работающий в двух школах, — две записи.

Проблема буквального чтения: при появлении единого аккаунта EduStore эти записи
придётся **сливать** — то есть выполнять ровно ту миграцию модели пользователя,
которой решение стремится избежать. Плюс расходится история: родитель с детьми в
двух школах сети — два профиля, два согласия, две ленты уведомлений.

Принято **AR-47 [дефолт]**: `User` глобален в инсталляции, телефон уникален
глобально, принадлежность школе — через `Membership`. Требование «внутри
workspace телефон уникален» при этом выполняется автоматически, а единый аккаунт
EduStore ложится на глобальную запись без слияния.

Цена решения названа честно: глобальная уникальность создаёт канал утечки факта
существования пользователя между школами («этот телефон уже зарегистрирован»).
Закрывается на уровне сценария входа — регистрация не сообщает о существовании
записи в другой школе, присоединение идёт по приглашению. Требование зафиксировано
как ворота **G-24**.

Владельцу: если нужен именно per-workspace пользователь (например, потому что
школы сети юридически не должны знать о пересечении контингента), решение
меняется на противоположное — тогда слияние при переходе на единый аккаунт
принимается как осознанная цена и заводится отдельным `[узел]`.

### Р3 · Что делать с уже написанным кодом внешнего IdP
Код OIDC-контура остаётся в репозитории и не удаляется этим решением: удаление —
это изменение, у которого должен быть свой план вывода (линза L-9). Он
переводится в статус неиспользуемого адаптера за портом **AR-50**; фактическое
удаление — отдельный инкремент вместе с переименованием полей `florus*`.
До тех пор `G-18` (живой OIDC-цикл) снимается: у неё больше нет предмета.
