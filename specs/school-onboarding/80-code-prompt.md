## Контекст

Ты реализуешь **Schoolium 1.1.1** — ERP для школы. Продукт и его границы описаны
в `docs/PRODUCT-LOGIC.md`. Все архитектурные решения пронумерованы и лежат в

   продукт, полный инвентарь того, что должно существовать (23 экрана, 15 модалок,
   9 типов кнопок, 11 моделей, 22 события, 13 прав, 27 кодов ошибок), сквозной
   сценарий приёмки и девять красных линий. Начинай с него и возвращайся к нему
   после каждого этапа — это чек-лист собственной работы.
1. `docs/PRODUCT-LOGIC.md` — что за продукт, модель тенантов, что не проектируется.
2. `docs/ar/INDEX.md` и восемь реестров в `docs/ar/` — принятые решения.

**Железные правила проекта:**

- Спека — источник истины. Расходишься со спекой — сначала правишь спеку, потом код.
- Не додумывай. Элемента нет в `70-screens.md` §10 — значит его нет. Поведение не
  описано — это дефект спеки: остановись и спроси, не изобретай (AR-18).
- Утверждение «работает» принимается только со ссылкой на зелёную проверку.
- Каждая мутация несёт право из каталога, каталог пополняется тем же коммитом (AR-35).

## Этап 0 — Генеральная проверка спеки (до единой строки кода)

**Режим: Opus, reasoning high. Кода на этом этапе не пишешь вообще.**

Задача: довести спеку до состояния, в котором реализация не потребует ни одного
вопроса. Ищи не опечатки, а **логические дыры**.

Прочитай документы 0–8 из списка выше целиком. Затем прогони материал по семи
линиям атаки; по каждой веди список находок:

1. **Источник истины.** Для каждой сущности (класс, ученик, группа, предмет,
   привязка, четверть, слот, урок, отметка, тема) назови единственного писателя и
   читателей. Два писателя без арбитра — находка. Данные, которые модалка
   расписания могла бы сохранить у себя вместо календаря, — находка (AR-68).
2. **Полнота FSM.** Возьми матрицу из `30-spec.md` и `model/states.mjs`. Для
   каждого из 13 состояний: есть выход, есть возврат, есть дом-экран, есть путь к
   `ready`. Отдельно проверь переходы, которых в матрице нет, но которые
   возможны в жизни: правка класса после генерации, удаление предмета с
   привязанным педагогом, деактивация педагога с уроками в сетке.
3. **Полнота таксономий.** Шесть ролей × шесть экранов; шесть значений отметок ×
   (средний балл, цвет, отчёт, гейт даты); семь кодов отказа генератора × (экран,
   текст, кнопка возврата). Пустая клетка — находка.
4. **Контракты.** Десять событий из `30-spec.md` и все эндпоинты из
   `70-screens.md`: у каждого поля есть владелец, обязательность и поведение при
   отсутствии. Каждый вызов имеет описанное поведение при недоступности стороны.
5. **Права и разделение обязанностей.** Каждое действие из `70-screens.md`
   сопоставь с правом. Отдельно: человек, совмещающий роли (AR-61) — может ли он
   пройти цикл в одиночку там, где не должен.
6. **Крайние случаи.** Пустые данные; одновременная работа двух устройств
   модератора; обрыв сети посреди мастера; праздник в первый день четверти;
   класс из одного ученика; группа из нуля учеников; педагог без нагрузки;
   предмет без педагога; ученик, добавленный после генерации расписания.
7. **Ложные утверждения.** Любое «проверено», «покрыто», «работает» в документах
   без ссылки на прогон или матрицу — вычёркивай как находку.

**Формат каждой находки:**

```
[🔴/🟡/🔵] <Место: файл, раздел>
Проблема: <что именно не определено или противоречит>
Последствие: <что сломается при реализации или в проде>
Решение: <конкретная правка спеки>
```

🔴 — сломает реализацию или прод. 🟡 — технический долг. 🔵 — улучшение.

**Затем — правки.** Все 🔴 и 🟡 закрываются правкой `30-spec.md` / `70-screens.md`
/ `60-design.md` немедленно. Если находка меняет архитектурное решение — заводи
новое `AR-81+` в нужный блок `docs/ar/` по правилам
`docs/method/AR-PROTOCOL.md` (сквозная нумерация, `next` в `INDEX.md`, ворота,
линзы) и помечай вытесненное как `[заменено AR-N]`. Требуется решение владельца —
оставляй `[узел]` и выноси вопрос в конец отчёта, а не решай за него.

**Ворота этапа 0 — все зелёные:**

```bash
npm run method:lint          # G-19…G-21, G-37, G-38
node specs/school-onboarding/model/walk.mjs
node specs/school-onboarding/model/props.mjs
node specs/school-onboarding/model/sim.mjs
```

Если правка спеки меняет FSM, генератор или журнал — **сначала обнови модель** в
`specs/school-onboarding/model/`, добейся, чтобы она падала на старом поведении и
проходила на новом, и только потом считай находку закрытой. Модель — это тест
спеки, и она обязана оставаться правдой.

**Выход этапа 0:** отчёт со всеми находками и их судьбой + обновлённые документы +
зелёные ворота. Коммит: `Этап 0: аудит спеки 1.1.1 — N находок закрыто`.
**К этапу 1 не переходишь, пока в спеке остаётся хоть одна открытая 🔴.**
