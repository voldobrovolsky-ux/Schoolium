# Генеральное описание Schoolium 1.1.1 — ориентир для сверки

> **Назначение.** Один документ, по которому агент проверяет себя: что за
> продукт, из чего он состоит, что обязано существовать к концу работы и чего в
> нём быть не должно. Это **не источник требований** — при расхождении
> побеждают `30-spec.md` (поведение), `70-screens.md` (экраны),
> `75-adaptive.md` (раскладки), `docs/ar/` (решения). Ориентир нужен, чтобы не
> потерять целое, разглядывая частное.
>
> Версия: **1.1.1**. Ветка-источник: `edustore-final-edition`.

---

## 1. Что мы строим, в трёх абзацах

**Schoolium** — ERP для школы: единственный существующий продукт экосистемы
**EduStore**, которая в будущем станет маркетплейсом образовательных сервисов.
Сейчас маркетплейса нет, есть сервис; Schoolium должен быть готов встать в него
позже, но витрина, каталог и биллинг EduStore сейчас не проектируются.

Версия 1.1.1 закрывает один сценарий целиком: **пустая школа превращается в
работающую**. Модератор школы заводит классы и учеников, создаёт предметы,
активирует сотрудников по QR, привязывает педагогов к предметам, задаёт четверти
и нагрузку, запускает автогенерацию расписания и подтверждает её. После этого
журнал получает колонки из расписания, и педагоги начинают ставить отметки.

Пользователи 1.1.1 — **только сотрудники школы**, шесть ролей. Аккаунтов детей и
родителей нет, детских персональных данных как учётных записей нет: ученик
существует записью контингента. Это сознательное снятие всего 152-ФЗ-контура с
первой версии; он вернётся в 1.1.3 вместе с кабинетами детей и родителей.

## 4. Сквозной сценарий приёмки

Версия считается работающей, когда этот путь проходится целиком без обращения к
разработчику — в **обеих** раскладках:

0. Школа и её первый модератор заведены платформенной операцией (AR-93);
   владелец передал директору одноразовую ссылку входа.
1. Модератор открывает ссылку на телефоне → сессия 90 дней; с ноутбука заходит
   на лендинг → «Вход» → `S-01` показывает QR → сканирует его телефоном из
   «Настройки → Подключить устройство» → ноутбук в кабинете.
2. Создаёт 8 классов без литер, по 15 учеников, 2 группы, 8 мальчиков → `S-11`;
   на шаге литер нажимает «⌀ Без литер», на шаге пола видит «Девочек: 7»,
   в превью читает перечень «1, 2, 3 … 8».
3. Заполняет профили учеников → `S-12`, `S-13`; список пересортировывается,
   строки окрашены по полу, «Ёлкина» встаёт после «Егорова».
4. Создаёт предметы на пары «предмет × класс» → `S-20`.
5. Активирует сотрудников: открывает карточку, показывает QR, сотрудник сканирует,
   вводит ФИО и телефон, пропускает фото → `S-31`, `S-03`, `S-04`. Сотрудник
   оказывается **в своём кабинете сразу** — сессия 90 дней выдана регистрацией
   (AR-91); домашний ноутбук он подключает сам по QR (`S-01` + `S-80`), а если
   потерял телефон — код с карточки у модератора (`S-05`).
6. Привязывает педагогов: «+» на карточке предмета, педагог сканирует из
   `S-70`, модератор выбирает «весь класс» либо группы → `S-21`, `S-22`.
7. Задаёт четыре четверти → `S-41` шаг 1; даты уходят в календарь.
8. Вписывает часы каждому педагогу → шаг 2; при перегрузе видит
   `LOAD_EXCEEDS_SANPIN` с именем класса и цифрами.
9. Отмечает приоритетные предметы либо жмёт «⌀ Без приоритетов» → шаг 3.
10. Задаёт параметры дня в границах СанПиН → шаг 4.
11. Запускает генерацию, видит предпросмотр, **нажимает «Подтвердить»** → `S-42`.
12. Журнал показывает колонки по материализованным урокам; 4 сентября с двумя
    уроками даёт две колонки под одним числом → `S-50`.
13. Педагог входит, открывает свой урок, задаёт тему, ставит отметки `5`, `н`,
    `б`; попытка поставить отметку в завтрашний урок отклоняется
    `LESSON_NOT_HELD` → `S-51`, `S-52`.
14. Модератор деактивирует ученика с отметками — история сохраняется, из новых
    колонок ученик исчезает.
15а. Модератор удаляет ошибочно созданный класс с пустыми профилями — класс
    исчезает целиком; класс, где есть отметки, отвечает `CLASS_HAS_MARKS`.
15б. Модератор деактивирует уволившегося педагога: привязки снимаются, предметы
    показывают неполное покрытие, расписание получает плашку «устарело»,
    выставленные им отметки остаются; попытка деактивировать единственного
    модератора отвечает `LAST_MODERATOR`.
15. Модератор добавляет ученика в середине четверти — плашка «расписание
    устарело» **не появляется**; затем меняет нагрузку, регенерирует и
    подтверждает — уроки с отметками остаются колонками с пометкой «вне
    расписания», отметки на месте (`S-50.col.detached`, AR-85).

**Ориентир по нагрузке:** полный онбординг школы 8×15 — около 65 минут работы
одного человека, из них ~40 минут ввод контингента (`model/sim.mjs`). Если
получается заметно дольше — где-то лишние касания.

## 5. Красные линии

Нарушение любой из них — не «спорное решение», а дефект:

1. **Система не решает за человека.** Расписание материализуется только после
   нажатия «Подтвердить». Автоприменение по таймеру или «раз всё зелёное» — запрещено (AR-18).
2. **Изоляция школ не обсуждается.** `workspaceId` на каждой таблице; общей
   таблицы поверх школ не существует ни для какого удобства (AR-2, AR-44).
3. **Гейт живёт в контракте, а не в интерфейсе.** Серые будущие колонки — это
   отражение проверки, а не сама проверка (AR-74).
4. **Смысл не кодируется одним цветом.** У отметок есть символ, у пола — позиция
   строки; человек с дальтонизмом должен всё различать (AR-80).
5. **Данные пересекают границу модуля только контрактом.** Прямой SQL в схему
   контингента или календаря запрещён (AR-45, AR-68).
6. **Литеральный hex в компоненте — дефект.** Только токены, иначе проверка
   контраста G-37 ничего не гарантирует.
7. **Недоступное роли не рендерится.** Пустое состояние не показывает кнопку,
   которой у роли нет (AR-69).
8. **Не додумывать.** Нет в спеке — значит нет; поведение не описано — это
   дефект спеки, о котором надо сообщить, а не заполнить собой.
9. **Разрушение называет свой объём.** Подтверждение удаления сообщает, что
   именно будет потеряно, числом — а не успокаивающей формулировкой, которая
   в опасном случае оказывается ложной (AR-105).
10. **История не переписывается пересборкой.** Отметка, поставленная человеком,
   переживает любую регенерацию расписания: урок отвязывается, а не удаляется
   (AR-85). Удаление отметки — только явное действие педагога.

## 7. Как сверяться

```bash
npm run method:lint      # реестры, линзы, спека, контраст, экраны, адаптация
node specs/school-onboarding/model/walk.mjs    # FSM: тупики, недостижимость
node specs/school-onboarding/model/props.mjs   # генератор, журнал, контингент
node specs/school-onboarding/model/sim.mjs     # нагрузка на модератора
```

Утверждение «готово» принимается только со ссылкой на зелёную проверку. Раздел
инвентаря §3 — чек-лист: каждая незакрытая строка означает, что версия не
собрана, даже если экраны выглядят законченными.
