# IDP — спецификация

**Статус: Draft.** Согласно FLOR-ADS §7.2 документ в статусе `Draft` нельзя отдавать
агенту в реализацию. Перевод в `Accepted` — после закрытия узлов раздела 16.

## 1. Назначение и границы

### 1.1 Задача

IDP отвечает на два вопроса и только на них:

1. **«Кто это»** — аутентифицировать субъекта и выпустить токен, которому доверяют
   продукты экосистемы.
2. **«Кто с кем связан»** — хранить факт объединения учётных записей в группы.

Потребители — продукты экосистемы (relying parties). IDP не является ни одним из них
и не содержит их бизнес-логики.

### 1.2 Границы

IDP **не**:

- не хранит роли и права продуктов — каждый продукт ведёт собственный каталог прав и
  сам назначает пакеты прав идентичности в своём контексте;
- не хранит тенантную структуру продуктов — тенант принадлежит продукту и ссылается
  на `identity_id` как на внешний ключ;
- не интерпретирует смысл группы — тип группы для IDP непрозрачная строка, заданная
  продуктом; фиксированного перечня типов в схеме IDP нет;
- не выводит из членства в группе никаких прав и никакой видимости данных;
- не содержит коммерческой логики — цен, подписок, скидок, расчётов;
- не содержит пользовательских интерфейсов продуктов; собственный UI IDP ограничен
  экранами аутентификации, согласия и управления своей учётной записью;
- не хранит предметных данных продуктов (успеваемость, расписание, переписка и т.п.).

Признак ошибки проектирования: в схему IDP предлагается добавить поле, осмысленное
только для одного продукта. Такое поле принадлежит продукту.

### 1.3 Стейкхолдеры

| Роль | Отношение к сервису |
|---|---|
| Владелец сервиса | принимает ADR, отвечает за SLO |
| Продукты-потребители | клиенты OIDC, потребители группового API |
| Пользователь | субъект персональных данных, управляет своей учётной записью |
| Оператор | эксплуатация, реакция на алерты |

## 2. Контекст и внешние интерфейсы

```
                    ┌───────────────────────────┐
   Пользователь ───▶│           IDP             │
   (браузер,        │  authorization server     │
    приложение)     │  token service            │
                    │  user store               │
                    │  session store            │
                    │  group store              │
                    └────────────┬──────────────┘
                                 │ OIDC / REST
                    ┌────────────┴──────────────┐
                    ▼                           ▼
            Продукт-потребитель A       Продукт-потребитель B
```

### 2.1 Таблица внешних интерфейсов

| Контрагент | Направление | Протокол | Контракт | Что ломается при отказе |
|---|---|---|---|---|
| Продукт-потребитель | входящее | OIDC (Authorization Code + PKCE) | `openapi.yaml`, discovery | Вход во все продукты. Уже выданные access-токены живут до истечения TTL — продукты продолжают работать в пределах этого окна |
| Продукт-потребитель | входящее | REST, групповое API | `openapi.yaml` | Операции с группами; аутентификация не затронута |
| Продукт-потребитель | исходящее | HTTP webhook | `asyncapi.yaml` | Продукт не узнаёт о блокировке/удалении идентичности вовремя; расхождение состояний до следующей синхронизации |
| Канал доставки кодов подтверждения | исходящее | [узел: канал не выбран] | — | Невозможно завершить операции, требующие подтверждения. Вход существующих пользователей не затронут |

**Правило контракта.** Граница между IDP и продуктами проходит по протокольному
контракту (discovery + userinfo + scopes + групповое API), а не по схеме данных.
Продукт **ОБЯЗАН** не знать внутренней схемы IDP. Это условие возможности менять
внутреннее хранение без ломки потребителей.

## 3. Контейнеры и правила зависимостей

### 3.1 Контейнеры

| Контейнер | Назначение | Технология |
|---|---|---|
| `idp-app` | authorization server, token service, групповое API, admin API | [дефолт] тот же язык/фреймворк, что и остальная экосистема |
| `idp-db` | постоянное хранение: identity, credentials, profile, devices, groups, audit | PostgreSQL |
| `idp-session-store` | сессии, одноразовые коды, rate-limit счётчики | Redis-совместимое хранилище с TTL |
| `idp-ui` | экраны входа, MFA, согласия, управления учётной записью | серверный рендеринг либо SPA |

### 3.2 Разделение горячего и холодного пути

Ключевое архитектурное требование, действующее с первого коммита независимо от
масштаба.

**Горячий путь** — проверка сессии, выпуск и валидация токена. **ОБЯЗАН** обходиться
сессионным хранилищем и локальной валидацией подписи по JWKS. **ОБЯЗАН** не читать
таблицы профиля.

**Холодный путь** — чтение и изменение профиля, устройств, групп, административные
операции. Идёт по отдельному маршруту и может быть тяжёлым.

Логическое разделение схем `core` / `credentials` / `profile` / `sessions` /
`devices` / `groups` **ОБЯЗАНО** быть заложено сразу, даже если физически это одна
инстанция БД. Стоимость разделения при старте близка к нулю; стоимость введения его
позже — миграция всего хранилища.

**Валидация токенов потребителями.** Продукты **ОБЯЗАНЫ** валидировать подпись
локально по кэшированному JWKS. Обращение к introspection на каждый запрос —
запрещено: оно превращает IDP в синхронную зависимость каждого запроса каждого
продукта.

### 3.3 Правила зависимостей

Формулировки проверяемые — каждая переходит в фитнес-функцию раздела 12.

1. Пакеты `domain/**` не импортируют ничего из `infrastructure/**`, `api/**`, `db/**`.
2. Модуль `groups/**` не импортирует ничего из `credentials/**`.
3. Модуль `credentials/**` не экспортирует наружу типы, содержащие поля класса
   `sensitive`.
4. Ни один модуль, кроме `credentials/**`, не обращается к таблицам схемы
   `credentials`.
5. Ни один модуль горячего пути не импортирует репозитории схемы `profile`.
6. Нет циклических зависимостей между модулями.

## 4. Модель данных

### 4.1 Identity

Ядро. Один человек в реальности — одна `Identity` на всю экосистему.

**Обоснование строгости.** Если продукты заводят собственные записи одного и того же
человека, кросс-продуктовые сценарии (например, доступ родителя к профилям детей,
находящихся в разных тенантах разных продуктов) становятся нереализуемыми, а склейка
идентичностей задним числом — миграцией с риском дублей и потери связей. Это
единственная сущность спецификации, цена ошибки в которой высока с первого дня.

| Поле | Тип | Класс | Правила |
|---|---|---|---|
| `id` | UUIDv4 или cuid | `internal` | Стабильный, непрозрачный, глобально уникальный. **ОБЯЗАН** не нести смысловой нагрузки. **ОБЯЗАН** никогда не переиспользовать идентификаторы продуктов. Не переиспользуется после удаления |
| `status` | enum | `internal` | См. §5.1 |
| `created_at` | timestamptz | `internal` | |
| `status_changed_at` | timestamptz | `internal` | |
| `retention_until` | timestamptz nullable | `internal` | Заполняется при переходе в `archived` |

`id` попадает в токен как `sub`. Никакое другое поле не является идентификатором
субъекта для продуктов.

### 4.7 Group

Генерик-контейнер. IDP не знает и не проверяет смысл группы.

| Поле | Тип | Класс | Правила |
|---|---|---|---|
| `id` | UUID | `internal` | |
| `tag` | text | `internal` | **Непрозрачная строка от продукта.** IDP не нормализует её, не ведёт справочник допустимых значений и не изменяет поведение в зависимости от значения |
| `created_by_client_id` | text | `internal` | Клиент-владелец группы |
| `audience` | text[] | `internal` | Перечень `client_id`, которым разрешено чтение группы. По умолчанию содержит только владельца. См. §4.8 |

Группа **ОБЯЗАНА** не иметь поля тенанта. Участники группы могут принадлежать разным
тенантам разных продуктов; это штатный случай, а не исключение.

### 4.8 Видимость группы

Проблема: групповое API общее для всех продуктов, а группы содержат сведения о
связях между людьми. Без явного ограничения любой продукт со scope `groups:read`
читает группы, созданные другим продуктом, — включая рабочие группы, само
существование которых является чувствительной информацией.

Решение: **группа читается только клиентами, перечисленными в `audience`.**
При создании `audience = [created_by_client_id]`. Расширение `audience` — операция
клиента-владельца, требующая scope `groups:write` и явного указания клиентов.
Запрос группы клиентом вне `audience` **ОБЯЗАН** возвращать `404`, а не `403`:
`403` подтверждает существование группы.

Это защита на транспорте, не замена продуктовому разграничению доступа. Членство в
группе по-прежнему не даёт прав ни на что (§4.9).

### 4.9 Membership

| Поле | Тип | Класс | Правила |
|---|---|---|---|
| `id` | UUID | `internal` | |
| `group_id` | FK | `internal` | |
| `identity_id` | FK | `internal` | |
| `role` | text | `internal` | **Непрозрачная строка от продукта.** Не влияет на поведение IDP |
| `status` | enum | См. §5.4 | |
| `joined_at` | timestamptz | `internal` | |

**Инвариант, обязательный к соблюдению во всей системе:**

> Членство в группе не даёт участнику никакого доступа к данным других участников
> и никаких прав ни в одном продукте.

IDP выдаёт факт связи. Что этот факт разрешает — решает продукт, отдельно для каждой
цели группы. Проектный пример коллизии, из-за которой инвариант введён: два
сотрудника в одной рабочей группе, при этом один из них не имеет права видеть
предметные данные, с которыми работает второй. Общее членство не должно давать этого
доступа ни при какой конфигурации.

## 5. Поведение и FSM-матрицы

### 5.1 FSM Identity

Матрица переходов:

| Из состояния | Событие | В состояние | Действие с данными | Побочные эффекты |
|---|---|---|---|---|
| — | создание | `active` | Создаётся `Identity`, при наличии — `Credential` | Аудит `identity.created` |
| `active` | блокировка администратором | `blocked` | `status`, `status_changed_at` | Все сессии удалены, все token family отозваны, вебхук потребителям, аудит |
| `active` | запрос удаления пользователем | `archived` | `status`, `retention_until = now + retention` | Все сессии удалены, все family отозваны, вебхук, аудит |
| `blocked` | снятие блокировки | `active` | `status` | Вебхук, аудит. Сессии не восстанавливаются |
| `blocked` | запрос удаления | `archived` | `status`, `retention_until` | Вебхук, аудит |
| `archived` | восстановление до истечения retention | `active` | `status`, `retention_until = null` | Вебхук, аудит |
| `archived` | истечение `retention_until` | `deleted` | Необратимое удаление: см. §5.2 | Вебхук, аудит |

Матрица полноты:

| Состояние | Есть выход? | Возврат на дом-экран? | Терминальное? |
|---|---|---|---|
| `active` | да: `blocked`, `archived` | да | нет |
| `blocked` | да: `active`, `archived` | нет — вход отклоняется с причиной | нет |
| `archived` | да: `active`, `deleted` | нет — вход отклоняется, предлагается восстановление до `retention_until` | нет |
| `deleted` | нет | нет — учётная запись не существует, вход неотличим от несуществующего пользователя | **да**, обоснованно: состояние достигается только по истечении retention и необратимо по определению |

Значение `retention` — [узел], определяется правовым основанием хранения.

### 5.2 Необратимое удаление

Мягкое удаление флагом не является доказанным удалением. Переход `archived → deleted`
**ОБЯЗАН** выполнять:

1. Физическое удаление строк `profile`, `credentials`, `devices` для идентичности.
2. Удаление `Membership` этой идентичности; группы, оставшиеся без участников,
   переводятся в `dissolved`.
3. Уничтожение ключа шифрования персональных полей идентичности (crypto-shredding) —
   способ сделать необратимыми данные в неизменяемых резервных копиях.
4. Сохранение в `core` минимальной записи-надгробия (`id`, `status=deleted`,
   `deleted_at`) — чтобы `id` не был переиспользован, а внешние ссылки продуктов
   разрешались в «удалён», а не в «не найден».
5. Сохранение записей аудита о самом удалении.

### 5.3 FSM TokenFamily

Матрица переходов:

| Из состояния | Событие | В состояние | Действие с данными | Побочные эффекты |
|---|---|---|---|---|
| — | выпуск после успешной аутентификации | `active` | Создаётся family, generation=0 | Аудит |
| `active` | предъявлен актуальный refresh | `active` | Предыдущий → `rotated`, новый generation | Аудит |
| `active` | вызван revocation endpoint / выход / смена пароля | `revoked` | Все токены family → `revoked` | Аудит |
| `active` | **предъявлен уже ротированный refresh** | `revoked` | Вся family отозвана целиком | **Аудит `token.reuse_detected`, алерт, сессии этой family удалены** |
| `active` | истечение срока | `expired` | — | — |

Матрица полноты:

| Состояние | Есть выход? | Возврат на дом-экран? | Терминальное? |
|---|---|---|---|
| `active` | да: `revoked`, `expired`, ротация | да | нет |
| `rotated` | нет — предъявление вызывает reuse-detection | нет | да, обоснованно: промежуточное состояние отдельного токена внутри живой family |
| `revoked` | нет | нет — требуется повторный вход | да, обоснованно |
| `expired` | нет | нет — требуется повторный вход | да, обоснованно |

Повторное предъявление ротированного токена трактуется как компрометация цепочки, а
не как ошибка клиента. Отзыв всей family обязателен.

### 5.4 FSM Group и Membership

Group:

| Из состояния | Событие | В состояние | Действие с данными | Побочные эффекты |
|---|---|---|---|---|
| — | создание клиентом | `active` | Создаётся группа, `audience=[владелец]` | Аудит |
| `active` | роспуск владельцем | `dissolved` | Все membership → `revoked` | Вебхук в `audience`, аудит |
| `active` | удаление последнего участника | `dissolved` | — | Вебхук, аудит |

| Состояние | Есть выход? | Возврат на дом-экран? | Терминальное? |
|---|---|---|---|
| `active` | да: `dissolved` | да | нет |
| `dissolved` | нет | нет — группа доступна только для чтения в аудите | да, обоснованно: восстановление создаёт неоднозначность состава |

Membership:

| Из состояния | Событие | В состояние | Побочные эффекты |
|---|---|---|---|
| — | приглашение создано | `pending` | Создаётся `Confirmation` |
| `pending` | подтверждение приглашённым | `active` | Вебхук в `audience`, аудит |
| `pending` | отклонение либо истечение `Confirmation` | `rejected` | Аудит |
| `active` | выход участника либо исключение владельцем | `revoked` | Вебхук, аудит |

| Состояние | Есть выход? | Возврат на дом-экран? | Терминальное? |
|---|---|---|---|
| `pending` | да: `active`, `rejected` | да — экран «ожидает подтверждения» | нет |
| `active` | да: `revoked` | да | нет |
| `rejected` | нет — требуется новое приглашение | да | да, обоснованно |
| `revoked` | нет — требуется новое приглашение | да | да, обоснованно |

Вступление в группу **ОБЯЗАНО** проходить через подтверждение приглашаемым. Продукт
не может добавить идентичность в группу односторонне.

### 5.5 FSM Confirmation

Единый механизм подтверждения. Отдельных протоколов под каждую операцию быть не
должно: каждая новая чувствительная операция — новый `purpose`, а не новый механизм.

| Из состояния | Событие | В состояние | Действие с данными | Побочные эффекты |
|---|---|---|---|---|
| — | инициирование | `pending` | Создаётся с `purpose`, `payload`, TTL, счётчиком попыток | Отправка кода/ссылки/QR |
| `pending` | верный код предъявлен субъектом | `confirmed` | — | Выполняется целевая операция, аудит |
| `pending` | отмена инициатором | `cancelled` | — | Аудит |
| `pending` | истечение TTL | `expired` | — | Аудит |
| `pending` | превышен лимит попыток | `expired` | — | Аудит, алерт при серии |

| Состояние | Есть выход? | Возврат на дом-экран? | Терминальное? |
|---|---|---|---|
| `pending` | да: `confirmed`, `cancelled`, `expired` | да — экран ожидания с возможностью отмены | нет |
| `confirmed` | нет — одноразовое | да | да, обоснованно |
| `cancelled` | нет | да | да, обоснованно |
| `expired` | нет | да — предлагается повторная инициация | да, обоснованно |

Требования:
- Подтверждение одноразовое: повторное предъявление `confirmed` — отказ и запись аудита.
- TTL — [дефолт] 10 минут для кодов, 24 часа для ссылок вступления в группу.
- Лимит попыток — [дефолт] 5, затем `expired`.
- Секрет подтверждения хранится хэшированным, как и refresh-токены.
- Целевая операция выполняется **только** при переходе в `confirmed`, атомарно с ним.

Перечень `purpose` открыт. Минимальный набор: `group.join`, `device.add`,
`identity.delete`, `email.verify`, `phone.verify`, `credential.reset`.

### 5.6 Enum-таксономии: значение → поведение

`Identity.status` — влияние на горячий путь:

| Значение | Вход | Существующие сессии | Групповое API | Виден продуктам |
|---|---|---|---|---|
| `active` | разрешён | действуют | доступно | да |
| `blocked` | отклонён с причиной | удалены | недоступно | да, со статусом |
| `archived` | отклонён, предложено восстановление | удалены | недоступно | да, со статусом |
| `deleted` | отклонён как несуществующий | нет | нет | как «удалён» |

`Credential.type` — влияние на уровень аутентификации:

| Значение | Достаточен как единственный фактор | Даёт AAL | Обязателен для админ-доступа |
|---|---|---|---|
| `password` | да | AAL1 | нет — недостаточен |
| `totp` | нет, только вторым фактором | AAL2 в паре с password | допустим |
| `webauthn` | да | AAL2 самостоятельно, AAL3 с аппаратным аутентификатором | **да** |

Целевой уровень: IAL1 + AAL2. Реализация AAL2 **ОБЯЗАНА** предлагать пользователю
фишинг-устойчивый вариант (WebAuthn), а не только TOTP.

### 5.7 Ключевые сценарии времени выполнения

**Вход пользователя в продукт.**
1. Продукт перенаправляет в `/authorize` с `code_challenge` (S256), `state`, `nonce`.
2. IDP аутентифицирует: пароль → при необходимости второй фактор.
3. Создаётся сессия, устанавливается SSO-cookie, возвращается `code` на точно
   совпадающий зарегистрированный `redirect_uri`.
4. Продукт обменивает `code` + `code_verifier` на токены в `/token`.
5. Продукт валидирует ID-токен локально по JWKS: подпись, `iss`, `aud`, `exp`,
   `nonce`.

**Вход во второй продукт при живой SSO-сессии.** Шаги 1, 3–5. Шаг 2 пропускается:
сессия найдена и её `aal` достаточен. Если требуемый `aal` выше достигнутого —
запрашивается только недостающий фактор (step-up), а не полный повторный вход.

**Обнаружение повторного использования refresh-токена.**
1. Предъявлен токен со `status = rotated`.
2. Вся family переводится в `revoked`, связанные сессии удаляются.
3. Запись аудита `token.reuse_detected`, алерт.
4. Клиенту возвращается ошибка `invalid_grant` без деталей.

**Вступление в группу.**
1. Продукт создаёт группу (или использует существующую) и `Membership` в `pending`.
2. IDP создаёт `Confirmation` с `purpose=group.join`, возвращает продукту ссылку/QR.
3. Приглашённый открывает ссылку, аутентифицируется, подтверждает.
4. `Membership → active` атомарно с `Confirmation → confirmed`.
5. Вебхук клиентам из `audience`.

**Отказ канала доставки подтверждений.** Операции, требующие подтверждения,
отклоняются с явной причиной и предложением повторить. Вход и работа существующих
сессий не затрагиваются. Деградация мягкая.

## 6. Протокольный контракт

Единственный поддерживаемый поток — **Authorization Code + PKCE (S256)**, для всех
типов клиентов, включая конфиденциальные. Implicit-flow и resource-owner-password
grant **ОБЯЗАНЫ** не предоставляться.

### 6.1 Endpoints

| Endpoint | Назначение | Примечания |
|---|---|---|
| `GET /.well-known/openid-configuration` | discovery | Публикация обязательна |
| `GET /.well-known/jwks.json` | публичные ключи | С `kid`; кэшируется клиентами |
| `GET /authorize` | старт потока | Обязательны `code_challenge`, `code_challenge_method=S256`, `state`, `nonce` |
| `POST /token` | обмен кода и ротация refresh | `grant_type`: `authorization_code`, `refresh_token` |
| `GET /userinfo` | профильные заявки | Состав ответа определяется выданными scope |
| `POST /revoke` | отзыв токена | Вызывается при выходе и смене пароля |
| `POST /introspect` | интроспекция | Для случаев, где локальная валидация неприменима. Не для каждого запроса |
| `GET /end-session` | выход из SSO-сессии | |

### 6.2 Требования к обработке `/authorize`

- `redirect_uri` сравнивается **точным совпадением строки**. Сопоставление по
  префиксу, шаблону или подстроке запрещено.
- `state` обязателен и проверяется клиентом.
- `nonce` обязателен и переносится в ID-токен.
- Авторизационный код одноразовый, TTL [дефолт] 60 секунд, привязан к `client_id` и
  `code_challenge`.

### 6.3 Токены

| Токен | Формат | TTL | Правила |
|---|---|---|---|
| ID-токен | JWT, подпись RS256 [дефолт] | = access | `aud` = `client_id`, содержит `nonce` |
| Access-токен | JWT, подпись RS256 [дефолт] | [дефолт] 10–15 мин | `aud` = конкретный resource server, не «все» |
| Refresh-токен | непрозрачная строка | [дефолт] 14–30 дней | Ротация при каждом использовании, reuse-detection, в БД только SHA-256 |

Ротация ключей подписи: перекрывающийся период, старый ключ остаётся в JWKS до
истечения максимального TTL выданных им токенов. `kid` обязателен всегда.

### 6.4 Дизайн scopes

Принципы: разделение по предметной области и чувствительности; иерархия
`область:действие`; чтение по умолчанию, запись — только явно; минимальная выдача.

| Scope | Даёт |
|---|---|
| `openid` | обязателен, `sub` |
| `profile:read` | имя, дата рождения, локаль |
| `profile:write` | изменение профиля |
| `email` | `email`, `email_verified` |
| `phone` | `phone_number`, `phone_number_verified` |
| `groups:read` | чтение групп, в `audience` которых входит клиент |
| `groups:write` | создание групп, управление составом и `audience` собственных групп |
| `devices:read` | список устройств |

Выдача scope конкретному клиенту — административная операция с фиксацией основания.
Клиент **ОБЯЗАН** не получать scope, не требуемый его сценарием. Экран согласия для
клиентов вне первой стороны **ОБЯЗАН** предъявляться; для клиентов первой стороны —
[дефолт] отключён.

### 6.5 Групповое API

| Метод | Путь | Scope | Примечания |
|---|---|---|---|
| `POST` | `/groups` | `groups:write` | Тело: `tag`, опционально `audience`. Владелец — вызывающий клиент |
| `GET` | `/groups/{id}` | `groups:read` | Только для клиентов из `audience`, иначе `404` |
| `PATCH` | `/groups/{id}/audience` | `groups:write` | Только владелец |
| `DELETE` | `/groups/{id}` | `groups:write` | Только владелец, переводит в `dissolved` |
| `POST` | `/groups/{id}/members` | `groups:write` | Создаёт `Membership` в `pending` и `Confirmation`; возвращает ссылку/QR |
| `DELETE` | `/groups/{id}/members/{identity_id}` | `groups:write` | Переводит в `revoked` |
| `GET` | `/identities/{id}/groups` | `groups:read` | Возвращает только группы, в `audience` которых входит вызывающий клиент |

`tag` и `role` передаются и возвращаются как есть. IDP **ОБЯЗАН** не валидировать их
против какого-либо перечня.

### 6.6 Ошибки

Схема ошибки единообразна для всего сервиса. Коды и условия перечисляются в
`openapi.yaml` поэндпоинтно. Требования:

- ошибки аутентификации **ОБЯЗАНЫ** не различать «пользователь не найден» и «неверный
  пароль»;
- ошибка при запросе несуществующей либо недоступной группы — `404` в обоих случаях;
- тело ошибки **ОБЯЗАНО** не содержать значений полей `personal` и `sensitive`.

## 7. Уведомление потребителей

Продукты **ОБЯЗАНЫ** узнавать об изменении статуса идентичности не только из отказа
токена — access-токен живёт до истечения TTL и после блокировки.

| Событие | Имя | Полезная нагрузка |
|---|---|---|
| Блокировка | `identity.blocked.v1` | `identity_id`, `occurred_at` |
| Разблокировка | `identity.unblocked.v1` | `identity_id`, `occurred_at` |
| Архивация | `identity.archived.v1` | `identity_id`, `retention_until` |
| Удаление | `identity.deleted.v1` | `identity_id`, `occurred_at` |
| Изменение состава группы | `group.membership.changed.v1` | `group_id`, `identity_id`, `status` |
| Роспуск группы | `group.dissolved.v1` | `group_id` |

Имя события — `<домен>.<сущность>.<действие-в-прошедшем-времени>` с версией.
События **ОБЯЗАНЫ** быть идемпотентными по `event_id`, доставка — с повторами и
экспоненциальной задержкой. Полезная нагрузка **ОБЯЗАНА** не содержать персональных
данных: потребитель читает нужное по правам.

## 8. Безопасность

### 8.1 Границы доверия

1. Браузер/приложение пользователя → IDP.
2. Продукт-потребитель → IDP.
3. IDP → БД и сессионное хранилище.
4. IDP → канал доставки подтверждений.
5. Оператор → административный интерфейс.

### 8.2 Модель угроз

| Граница | STRIDE | Угроза | Митигация | Проверка |
|---|---|---|---|---|
| 1 | Spoofing | Фишинг учётных данных | WebAuthn как фишинг-устойчивый фактор; привязка credential к origin | Наличие WebAuthn-пути в e2e |
| 1 | Elevation | Перехват авторизационного кода | PKCE S256 обязателен; точное совпадение `redirect_uri`; одноразовый код с коротким TTL | Тест: подмена `redirect_uri` отклонена |
| 1 | Spoofing | Подбор пароля | Rate-limit по идентичности и по IP; лимит попыток; неразличимые сообщения об ошибке | Тест лимитов |
| 2 | Elevation | Клиент запрашивает избыточные scope | Реестр разрешённых scope на клиента; выдача сверх реестра отклоняется | Тест: запрос неразрешённого scope отклонён |
| 2 | Information disclosure | Продукт читает чужие группы | `audience`-фильтрация, `404` вне `audience` | Тест: чужая группа недоступна |
| 2 | Spoofing | Кража refresh-токена | Ротация + reuse-detection с отзывом family; короткий access | Тест reuse-detection |
| 3 | Information disclosure | Компрометация дампа БД | Argon2id для паролей; SHA-256 для токенов; шифрование `personal` at rest, ключи вне БД | Тест: в дампе нет сырых секретов |
| 3 | Tampering | Подделка записи аудита | Append-only, запрет UPDATE/DELETE на уровне прав БД | Тест: UPDATE отклонён |
| 4 | Information disclosure | Перехват кода подтверждения | Короткий TTL, одноразовость, лимит попыток, хэширование секрета | Тест повторного предъявления |
| 5 | Elevation | Компрометация административного доступа | Обязательный WebAuthn для админ-ролей; каждое действие в аудите | Тест: вход админа без WebAuthn отклонён |

Модель угроз **ОБЯЗАНА** пересматриваться при каждой новой интеграции — новая
интеграция создаёт новую границу доверия.

### 8.3 Три уровня прав

1. **Административный доступ к IDP** — управление клиентами, ключами, статусами
   идентичностей. Модель — RBAC. Фишинг-устойчивый второй фактор обязателен. Каждое
   действие в аудите с указанием актора.
2. **Права клиентов** — OAuth scopes, §6.4. Реестр «клиент → разрешённые scope»
   ведётся явно.
3. **Права пользователя над своей учётной записью** — список активных сессий и
   устройств, отзыв конкретной сессии/устройства, выход со всех устройств, управление
   факторами, просмотр и отзыв согласий, запрос удаления.

ABAC и графовые модели доступа не вводятся: предметная задача IDP их не требует.
Введение — только через ADR при появлении обоснованной потребности.

### 8.4 Хранение секретов

| Что | Как |
|---|---|
| Пароль | Argon2id. [дефолт] `m=19 MiB, t=2, p=1`, калибровка под фактическое железо с целевым временем верификации ≈100 мс. Число одновременных верификаций **ОБЯЗАНО** быть ограничено семафором: пиковое потребление памяти = `m × лимит` и должно помещаться в бюджет RAM инстанса |
| Refresh-токен | SHA-256 в БД, сырой не хранится |
| Секрет подтверждения | так же |
| `client_secret` | хэширование |
| TOTP-секрет | шифрование at rest |
| Ключи подписи | вне БД, ротация с перекрытием |
| Ключи шифрования PII | вне БД, отдельный носитель; уничтожение ключа — механизм необратимого удаления (§5.2) |

### 8.5 Локализация и сроки хранения

Первичный сбор, запись, систематизация, накопление и хранение персональных данных
граждан РФ **ОБЯЗАНЫ** выполняться в базах данных на территории РФ. Требование
распространяется на резервные копии и на любые внешние сервисы, через которые
персональные данные проходят.

**ОБЯЗАНЫ** существовать: опубликованная политика обработки персональных данных,
назначенный ответственный, срок хранения для каждого поля класса `personal` с
указанием правового основания, реализованный путь необратимого удаления (§5.2).

## 9. Сценарии качества

| # | Атрибут | Сценарий | Приоритет | Проверяется |
|---|---|---|---|---|
| Q1 | Производительность | При штатной нагрузке проверка сессии на горячем пути выполняется без обращения к схеме `profile` | высокий | Фитнес-функция FF-5 |
| Q2 | Производительность | Пиковый одновременный вход не приводит к исчерпанию памяти инстанса | высокий | Нагрузочный тест с семафором Argon2id |
| Q3 | Доступность | Отказ канала доставки подтверждений не влияет на вход и работу существующих сессий | высокий | Тест деградации |
| Q4 | Безопасность | Повторное предъявление ротированного refresh отзывает всю family | высокий | Тест reuse-detection |
| Q5 | Безопасность | Клиент вне `audience` не может установить существование группы | высокий | Тест: ответ `404`, а не `403` |
| Q6 | Изменяемость | Добавление продукта-потребителя не требует изменения схемы IDP | средний | Ревью ADR |
| Q7 | Наблюдаемость | По записям аудита восстанавливается полная последовательность событий инцидента компрометации | высокий | Разбор учебного инцидента |

Сценарий без проверки **ОБЯЗАН** помечаться `не покрыт` и дублироваться строкой в
разделе 16.

## 10. Надёжность

| SLI | Определение | SLO | Окно | Бюджет ошибок |
|---|---|---|---|---|
| Доступность `/token` | доля ответов с кодом < 500 | 99.9% | 28 дней | 40 мин |
| Доступность `/authorize` | доля ответов с кодом < 500 | 99.9% | 28 дней | 40 мин |
| Задержка валидации сессии | доля быстрее 100 мс | 99.0% | 28 дней | — |
| Задержка входа с паролем | доля быстрее 500 мс | 95.0% | 28 дней | — |
| Доставка вебхуков | доля доставленных за 60 с | 99.0% | 28 дней | — |

Политика бюджета ошибок: **при исчерпании бюджета за скользящее окно все изменения,
кроме исправлений инцидентов и уязвимостей, останавливаются до возвращения сервиса в
рамки SLO.**

Минимальный набор ранбуков: отказ БД, отказ сессионного хранилища, компрометация
ключа подписи, всплеск reuse-detection, исчерпание бюджета ошибок, откат релиза.

## 11. Управление изменениями

**Миграции схемы** — только по схеме «расширение → перенос → сжатие». Каждая миграция
описывается парой «вперёд/назад». Необратимая миграция требует ADR.

**Версионирование интерфейсов** — семантическое. Ломающим считается изменение, при
котором корректный потребитель предыдущей версии перестаёт работать: удаление или
переименование заявки, сужение типа, ужесточение валидации, изменение семантики
значения, удаление кода ответа. Добавление необязательного поля ломающим не является;
добавление обязательного поля во входной контракт — является.

**Деприкация:** ADR со статусом Accepted → отметка `deprecated` в спецификации →
заголовки `Deprecation` и `Sunset` → поимённое уведомление каждого потребителя из
каталога → срок ожидания для Tier 0 90 дней с момента подтверждения получения
уведомления последним потребителем → отключение. Отключение интерфейса, у которого по
телеметрии остались потребители, запрещено независимо от истечения срока.

**Фиче-флаги** — таблица «флаг → назначение → владелец → дата планового удаления».
Флаг без даты удаления не создаётся.

## 13. Наблюдаемость

### 13.1 Логи

Структурированные. Обязательные поля: время, уровень, идентификатор трассировки,
`client_id`, тип события, исход.

**Маскируются всегда:** все поля класса `personal` и `sensitive` из раздела 4 —
`email`, `phone`, `family_name`, `given_name`, `middle_name`, `birthdate`,
`fingerprint`, `last_ip`, `ip`, `user_agent`, `Credential.secret`. Список **ОБЯЗАН**
поддерживаться в соответствии с разделом 4 фитнес-функцией FF-8.

Токены, коды подтверждения и авторизационные коды **ОБЯЗАНЫ** не попадать в логи ни в
каком виде, включая усечённый.

### 13.2 Аудит

Минимальный перечень типов событий:

`identity.created`, `identity.blocked`, `identity.unblocked`, `identity.archived`,
`identity.deleted`, `auth.login.success`, `auth.login.failure`, `auth.mfa.challenge`,
`auth.mfa.failure`, `session.created`, `session.revoked`, `token.issued`,
`token.rotated`, `token.revoked`, `token.reuse_detected`, `credential.added`,
`credential.removed`, `device.added`, `device.revoked`, `confirmation.created`,
`confirmation.confirmed`, `confirmation.expired`, `group.created`, `group.dissolved`,
`membership.created`, `membership.revoked`, `group.audience.changed`,
`client.scope.granted`, `admin.action`.

### 13.3 Проверки здоровья

Проба **ОБЯЗАНА** не отвечать «жив», если недоступна зависимость, без которой сервис
не выполняет свою функцию. Раздельно: liveness (процесс), readiness (БД и сессионное
хранилище доступны, ключи подписи загружены).

### 13.4 Алерты

Каждый алерт ссылается на ранбук. Минимум: всплеск `token.reuse_detected`, всплеск
`auth.login.failure`, недоступность БД или сессионного хранилища, приближение к
исчерпанию бюджета ошибок, приближение срока ротации ключа.

## 14. Единый язык

| Термин | Значение в IDP | Отличие от одноимённого в продуктах |
|---|---|---|
| Identity | Учётная запись человека в экосистеме | В продуктах «пользователь» — обычно запись продукта, ссылающаяся на `identity_id`, вместе с ролями и принадлежностью тенанту |
| Группа | Контейнер связей между Identity, без встроенного смысла | В продуктах «группа» — предметная сущность со своими правилами доступа |
| Роль | В IDP: только административная роль внутри самого IDP; `Membership.role` — непрозрачная строка продукта | В продуктах «роль» — пакет прав в каталоге продукта |
| Сессия | Серверная запись факта аутентификации | В продуктах — обычно сессия приложения, живущая по своим правилам |
| Клиент | Продукт, зарегистрированный как OAuth-клиент | В продуктах «клиент» — заказчик или организация |

Расхождение значений этих терминов между IDP и продуктами — типовой источник дефектов
интеграции. Таблица обязательна к сверке при подключении каждого нового продукта.

## 15. Решения к оформлению

Каждое **ОБЯЗАНО** быть оформлено отдельным ADR по шаблону FLOR-ADS с обязательным
разделом «Рассмотренные варианты».

| # | Решение |
|---|---|
| ADR-A | Authorization Code + PKCE как единственный поток; отказ от implicit и password grant |
| ADR-B | Ротация refresh-токенов с reuse-detection и отзывом всей family |
| ADR-C | Argon2id как алгоритм хранения паролей; параметры и ограничение параллелизма |
| ADR-D | Разделение горячего и холодного пути на уровне схем БД с первого коммита |
| ADR-E | Отсутствие ролей и прав продуктов в IDP |
| ADR-F | Группа как генерик-контейнер с непрозрачным тегом; отсутствие перечня типов в схеме |
| ADR-G | Группа не привязана к тенанту |
| ADR-H | Видимость группы через `audience`; `404` вместо `403` вне `audience` |
| ADR-I | Единый механизм подтверждения вместо протокола на каждую операцию |
| ADR-J | Необратимое удаление через crypto-shredding; запись-надгробие |
| ADR-K | Обязательный фишинг-устойчивый фактор для административного доступа |
| ADR-L | Отказ от SAML, SCIM, графовых моделей доступа и sender-constrained токенов в текущем объёме |

## 16. Узлы, риски и отложенное

### 16.1 Открытые узлы

Требуют решения владельца до перевода документа в `Accepted`. Реализация при
незакрытом узле запрещена.

| # | Узел |
|---|---|
| N1 | Канал доставки подтверждений: какой именно, кто провайдер, что при его отказе |
| N2 | Срок хранения `retention` для `archived` и правовое основание |
| N3 | Первичный идентификатор входа: email, телефон, оба, что из них обязательно |
| N4 | Требуется ли самостоятельная регистрация пользователем, либо все идентичности создаются продуктом |
| N5 | Обязателен ли второй фактор для обычного пользователя, или только предлагается |
| N6 | Порядок регистрации нового продукта как OAuth-клиента и выдачи ему scope |
| N7 | Что происходит с группами и членством при блокировке идентичности: сохраняются или приостанавливаются |
| N8 | Разрешено ли одной идентичности состоять в двух группах с одинаковым `tag` от одного клиента |

### 16.2 Риски и долг

| Риск | Влияние | Митигация | Владелец |
|---|---|---|---|
| Продукт заведёт собственную запись человека вместо ссылки на `identity_id` | Кросс-продуктовые сценарии становятся нереализуемыми; склейка — тяжёлая миграция | Проверка при подключении каждого клиента; фиксация в контракте потребителя | Архитектура |
| Параметры Argon2id при пике входов исчерпают память инстанса | Отказ сервиса в момент максимальной нагрузки | Семафор на число одновременных верификаций; нагрузочный тест до релиза | Владелец сервиса |
| Продукт начнёт трактовать членство в группе как основание доступа | Утечка данных между участниками группы | Инвариант §4.9 в контракте; проверка при ревью каждого потребителя | Архитектура |
| Единственная инстанция БД — единая точка отказа для входа во все продукты | Недоступность всей экосистемы | Резервное копирование и проверяемое восстановление; реплики по метрикам | Оператор |
| Просроченные ключи шифрования PII без процедуры ротации | Невозможность ротации без простоя | Процедура ротации до первого продакшн-релиза | Оператор |

### 16.3 Отложенное

Вводится по наступлению условия, не заранее. Условие — часть решения об отказе.

| Что | Условие введения |
|---|---|
| Реплики чтения, шардирование | По метрикам: первичный узел не справляется с записью либо задержка чтения вне SLO |
| SCIM | Потребителю требуется автоматический провижининг и деинициализация, а не только вход |
| SAML | Появился потребитель, требующий именно его |
| Графовая модель доступа | Появилась потребность в разделении конкретных объектов между конкретными пользователями |
| Sender-constrained токены (DPoP/mTLS) | Инциденты с уводом токенов либо работа с особо чувствительными данными |
| Экран согласия для клиентов вне первой стороны | Появление первого такого клиента |

## 17. Критерии готовности

**Документ готов к переводу в `Accepted`:** закрыты все узлы §16.1; каждое решение
§15 оформлено ADR; `openapi.yaml` и `asyncapi.yaml` заполнены и валидны.

**Реализация готова к присвоению Tier 0:** модель угроз построена по всем границам
доверия; схемы событий вынесены в реестр схем экосистемы; потребительские контракты
верифицируются как гейт деплоя; ранбуки покрывают минимальный набор §10;
фитнес-функции §12 выполняются в CI и блокируют мерж; каждый потребитель сервиса
идентифицирован поимённо в каталоге.

**Отдельно проверяется до первого продакшн-релиза:**
- дамп БД не содержит сырых паролей, токенов и незашифрованных полей `personal`;
- повторное предъявление ротированного refresh отзывает всю family;
- клиент вне `audience` не может отличить существующую группу от несуществующей;
- удалённая идентичность неотличима от несуществующей на пути входа;
- отказ канала подтверждений не влияет на вход;
- пиковый вход не исчерпывает память инстанса.
