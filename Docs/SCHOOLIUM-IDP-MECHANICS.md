# Schoolium ↔ IDP — механика интеграции

Компаньон к спеке IDP. Показывает, где в реальных сценариях Schoolium вызывает IDP и почему.

## Разделение: что своё у Schoolium, что приходит из IDP

| | Schoolium | IDP |
|---|---|---|
| «Это Иванова Мария» | не хранит — ссылается на `identity_id` | хранит: Identity, credentials, профиль |
| «Мария — модератор школы №5» | хранит: `WorkspaceMembership(identity_id, workspace_id, role)` | не знает — `role` для IDP непрозрачен |
| «Школа №5 существует, статус active» | хранит: `Workspace` | не знает — тенантов в IDP нет вообще |
| «Мария и её муж — родители Пети» | не хранит напрямую | хранит: `Group(tag="family")`, `Membership(role="parent")` |
| «Мария вошла в систему» | читает `sub` из ID-токена IDP | выдаёт токен, ведёт сессию |
| «Может ли Мария читать оценки» | хранит: собственный каталог прав Schoolium | не участвует вообще |

Правило одной строкой: **IDP отвечает «кто это» и «кто с кем связан», Schoolium отвечает на все вопросы «что это значит для школы».**

## Сущности Schoolium, которых в IDP нет

### Workspace
Школа. Собственная таблица Schoolium. Состояния `creating → created → deleted` (спека тенантности Schoolium) — IDP их не видит и не участвует в переходах.

### WorkspaceMembership
```
identity_id   → FK на Identity.id из IDP, ничего больше об этом человеке Schoolium не хранит
workspace_id  → FK на Workspace
role          → значение из собственного каталога прав Schoolium (не IDP)
status
```
Одна Identity может иметь несколько `WorkspaceMembership` одновременно, в разных `workspace_id`, с независимыми `role` в каждом — человек может быть модератором в одной школе и родителем в другой.

Это ядро того, «что человек может делать в конкретной школе». `WorkspaceMembership.role` — не то же самое, что `Membership.role` в IDP: одно про принадлежность школе, другое про членство в IDP-группе (семье, рабочей группе). Два разных membership, случайно совпадающее имя поля.

### Каталог прав Schoolium
Гранулярный, не «админ/пользователь» — модель наборов прав (как в 1С). Роль в Schoolium — пакет прав из каталога Schoolium, назначенный конкретной `WorkspaceMembership`. Супер-админ Schoolium — не отдельный тип Identity в IDP, а Identity с максимальным пакетом прав платформенного уровня в каталоге Schoolium. Устройство самого каталога (наборы, наследование, кто редактирует) — отдельная спека, не эта.

## Сценарий 1 — создание школы и провижининг модератора

1. Супер-админ (аутентифицирован через IDP) вызывает Schoolium: «создать школу» → Schoolium создаёт `Workspace(status=creating→created)`. IDP не вызывается — чисто Schoolium-операция.
2. Супер-админ вводит контакт будущего школьного модератора → Schoolium вызывает IDP: создаёт `Confirmation(purpose="identity.invite")`, IDP отправляет код/ссылку.
3. Приглашённый подтверждает → используется существующая Identity, если она уже есть, иначе IDP создаёт новую. Одна Identity на человека — ради этого приглашение идёт через IDP, а не заводится локальной записью Schoolium.
4. Schoolium получает `identity_id` и у себя создаёт `WorkspaceMembership(identity_id, workspace_id, role="moderator")`.
5. `Workspace` переходит в состояние с назначенным модератором (детали в спеке тенантности Schoolium).

## Сценарий 2 — вход в Schoolium

1. Пользователь открывает Schoolium → редирект на IDP `/authorize` с PKCE.
2. После аутентификации Schoolium получает ID-токен, `sub` = `identity_id`.
3. Schoolium ищет `WorkspaceMembership` по этому `identity_id` — несколько → выбор школы; одна → открывается сразу.
4. Дальше всё внутри Schoolium решается по `WorkspaceMembership.role` и каталогу прав Schoolium. IDP больше не участвует до истечения токена.

Schoolium не хранит и не проверяет пароли сам — доверяет токену IDP и дальше работает со своими данными.

## Сценарий 3 — привязка семьи (кросс-тенантно)

Пример: мама и папа, Саша учится в школе №1, Матвей — в школе №2, обе школы — Workspace в Schoolium.

1. У Саши и Матвея уже есть `Identity` + `WorkspaceMembership` каждый в своей школе (`role="student"`).
2. Родитель инициирует «привязать ребёнка» → Schoolium вызывает IDP: создать/переиспользовать `Group(tag="family", audience=["schoolium"])`, добавить `Membership(role="parent")` для родителя, `Membership(role="child")` для Саши и Матвея.
3. Подтверждение — `Confirmation(purpose="group.join")`, QR или ссылка.
4. После подтверждения Schoolium у себя собирает картину: родитель состоит в IDP-группе с Сашей и Матвеем → Schoolium подтягивает данные обоих детей из их `WorkspaceMembership` (в разных Workspace) и показывает объединённо.

IDP не знает про школы вообще — только факт связи людей. Картину по школам собирает Schoolium.

Что именно видит родитель у ребёнка в другой школе (весь профиль или сводка) — решает владелец Schoolium отдельно, здесь не зафиксировано.

## Сценарий 4 — почему членство не даёт доступа (директор/психолог)

Оба — Identity с `WorkspaceMembership` в одной школе (`role="director"` и `role="psychologist"`).

1. Директор создаёт рабочую группу в IDP: `Group(tag="workgroup", audience=["schoolium"])`, приглашает психолога — `Membership(role="member")` для обоих.
2. Это даёт только факт связи (например, для общего чата по методичке).
3. Ничего в этом членстве не меняет права психолога или директора внутри Schoolium. Доступ психолога к записям консультаций регулируется исключительно `WorkspaceMembership.role` и каталогом прав Schoolium — директор не получает к ним доступ, даже состоя с психологом в одной IDP-группе.

Реализация «раз они в одной группе — дать общий доступ» нарушает инвариант IDP §4.9 и является дефектом, а не фичей.
